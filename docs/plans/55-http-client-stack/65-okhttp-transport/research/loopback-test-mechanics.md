# Scripting and asserting the transport's Level 3 and Level 4c scenarios against `mockwebserver3`, and the shape of the four loopback fixtures

## Question

How is each Level 3 (integration) and Level 4c (non-functional) scenario of the OkHttp transport scripted and asserted against `mockwebserver3` 5.5.0 (server script, client call, assertion), and what must the four published loopback fixtures (`LoopbackTransports`, `MockWebServer.webtoolsUrl(path)`, `Fixture.toMockResponse()`, `MockWebServer.enqueue(fixture)`) do?

A usable answer must hold under these requirements: plain-HTTP loopback on real time under `runBlocking`; no fixed port; every server closed; Windows, Linux and macOS; nothing that needs the network; Java 11 API only (`-Xjdk-release=11`, tests included); JUnit Jupiter 5.10.1, so `@StartStop` is unavailable; the fixtures keep their three published dependencies (`webtools-http`, `kotlinx-coroutines-test` 1.10.2, `mockwebserver3` 5.5.0); `-Xexplicit-api=strict` with KDoc on every public declaration.

How the evidence was gathered. Source is `mockwebserver3` and `okhttp-jvm` 5.5.0 at tag `parent-5.5.0` of `square/okhttp`. "Measured" means a throwaway probe run outside the repository on Windows 11, JDK 23.0.2, Gradle 9.7.1, Kotlin 2.2.0, `okhttp-jvm` 5.5.0, `mockwebserver3` 5.5.0, `okhttp-tls` 5.5.0. The probe used a plain `OkHttpClient` configured as the transport will be (`retryOnConnectionFailure(false)`, `followRedirects(false)`, a private `Dispatcher` and `ConnectionPool`, a network interceptor hiding `Retry-After` on a `503`), because the transport itself is not built yet. Nothing was measured on Linux or macOS (see Gaps).

## Bottom line

- **Scripts.** Every required scenario is expressible with the default `QueueDispatcher` plus `MockResponse.Builder` (`SocketEffect.CloseSocket` on `onResponseStart`, `throttleBody`, `headersDelay`, `chunkedBody`, a hand-written `MockResponseBody` for an endless body), or with one small custom `Dispatcher` for the unbounded redirect chain. The assertion is `requestCount` (read after the call returns; the server counts a request when it has read it, before it dispatches a response) plus `takeRequest(timeout)` for headers and `connectionIndex`/`exchangeIndex`.
- **Forcing a new connection:** have the server send `Connection: close` (measured: a second DNS lookup in 10 of 10 runs). Do not use `SocketEffect.CloseSocket` on `onResponseEnd` for this: the client reuses the dead pooled connection and fails without a new lookup (0 of 10).
- **`close()` lets the JVM exit:** launch a child JVM from the test (`java.home` plus `java.class.path`, both correct inside a Gradle 9.7.1 test worker; measured 0.4 s to exit when `close()` shuts the dispatcher down, still alive after 12 s when it does not). Recommended over a thread check, which cannot tell a missed thread from a thread that has not finished exiting and depends on OkHttp's thread names.
- **`webtoolsUrl(path)`** names the bound address as an IP literal (`socketAddress.address.hostAddress`; IPv6 bracketed), never `hostName`/`url()`: both of those call `getHostName()`, which reverse-resolves an address that was not created from a name. `127.0.0.1` and `::1` are exactly the literals the relaxation admits with its port exemption. The helper uses `http` and builds on the bound address, so it is correct however the consumer started the server.
- **`toMockResponse()`** must derive framing from the body: `Content-Length` and `Transfer-Encoding` are not copied; a `204`/`205` gets neither a body nor a `Content-Length` (OkHttp rejects a non-zero one); a `304`, and a response to `HEAD`, write no body and keep (or derive) the declared length; a `1xx` fixture is refused (OkHttp waits for the real response and times out). Everything else is written as given, `Content-Encoding`, `Connection` and `Keep-Alive` included. `enqueue(fixture)` fails fast with a clear message when a custom `Dispatcher` is set (the member `enqueue` otherwise throws a bare `ClassCastException`).
- **Kotlin shape:** `object LoopbackTransports { fun untrusted(userAgent, policy = ..., resolve = ...): OkHttpTransport; fun trusted(...) }` with `resolve: (host: String) -> List<InetAddress>` as the last parameter, so `LoopbackTransports.untrusted("agent") { listOf(loopback) }` reads naturally. A function type, not a `fun interface` and not `okhttp3.Dns`. The one HTTPS test adds `okhttp-tls` 5.5.0 to the module's `jvmTest` only and builds the internal constructor directly with a donor client carrying the trust.

## Findings

### F1. What `requestCount` counts (documented source + measured)

Evidence tier: documented (source at `parent-5.5.0`) and measured.

`MockWebServer.requestCount` is incremented in `processOneRequest` immediately after `readRequest` returns and before the dispatcher is asked for a response:

- A request the server read in full and then disconnected on (response `onResponseStart(CloseSocket())`) **is counted** (measured: seed `200`, then a dropped request: `requestCount` 2; both recorded requests had `connectionIndex` 0 and `exchangeIndex` 0 then 1, proving reuse of one pooled connection).
- A truncated request head is counted (measured 1; `RecordedRequest.failure` is non-null).
- A response whose `onRequestStart` is `CloseSocket` is counted at accept time without any request being read (measured 1, the client got `unexpected end of stream`). A server script that uses it counts a request that never arrived.
- A TCP connection that sends nothing is not counted (measured 0; the server logs a `didn't make a request` warning through `java.util.logging`, harmless).
- Because the increment precedes the response, after a client call has returned the count of every exchange that call made is final, so `assertEquals(n, server.requestCount)` needs no settling delay. `takeRequest(timeout, unit)` returns `null` on timeout and its queue also receives the bookkeeping requests above; `takeRequest()` without a timeout blocks without bound and is not used.
- With the default `QueueDispatcher` an unscripted extra request blocks in `responseQueue.take()` until the client times out (it is still counted). `(dispatcher as QueueDispatcher).setFailFast(true)` answers it `404` at once, which turns a hidden re-send into a fast, visible failure.

### F3. Level 4c scripts and the endless body (measured)

- **Endless body.** `MockResponseBody` has `contentLength` (`-1` if unknown) and `writeTo(sink)`; the server writes it straight to the socket, so a chunked endless body must write its own chunk framing. A body that loops `sink.writeUtf8("400\r\n"); sink.write(oneKiB); sink.writeUtf8("\r\n"); sink.flush()` until the write throws, records bytes written, and counts down `stopped` in a `finally`, is paired with `removeHeader("Content-Length")` and `addHeader("Transfer-Encoding","chunked")`. An unframed variant (no `Content-Length`, no `Transfer-Encoding`, no chunk framing) is delimited by close and also stops when the client leaves (measured). The thread ends when the socket closes; `server.close()` closes open sockets, so a stuck writer cannot hang `close()`.
- **Endless chunked body ended by the cap.** Call with `maxResponseBytes` 1 000 000; result `BodyTooLarge`; `stopped.await(5, SECONDS)` true. The server may have written megabytes before it notices (measured 8 MiB on loopback with no pacing), so assert only that the writer stopped, never a byte bound. Add `throttleBody(65536, 10, MILLISECONDS)` if a bounded overshoot matters.
- **Slow drip ended by the call timeout.** `Builder().body("x".repeat(100_000)).throttleBody(10, 100, TimeUnit.MILLISECONDS)` (about 100 bytes per second), policy `settings { callTimeout = 1.seconds; readTimeout = 10.seconds }`. Result `Timeout`; elapsed about 1 s (measured 1013 ms with a 1 s limit), asserted `< 3 s` and `>= 0.9 s`. The `readTimeout` must exceed the drip interval, otherwise the read timeout fires first and the test proves the wrong thing (existing finding, `http-transport.md` F7: with a 500 ms read timeout the drip ran 5.3 s). `server.close()` afterwards takes tens of milliseconds, because `ThrottledSink` sleeps through `socket.sleepWhileOpen`, which polls for a closed socket every 100 ms.
- **`headersDelay`.** `headersDelay(3, SECONDS)` with a 700 ms call timeout ended in 713 ms (measured); `bodyDelay` is the analogous knob after the headers.
- **Redirect chain over the cap.** `server.dispatcher = object : mockwebserver3.Dispatcher() { override fun dispatch(request: RecordedRequest) = MockResponse.Builder().code(302).addHeader("Location", server.webtoolsUrl("/${n + 1}").toString()).build() }` where `n` is parsed from `request.url.encodedPath`. With `maxRedirects = 3`: `TooManyRedirects(3)` after exactly `requestCount == 4`. The dispatcher is the right tool for an unbounded chain; queueing `maxRedirects + 2` responses also works but hides a runaway loop behind a blocked queue.
  Import caution: `mockwebserver3.Dispatcher` and `okhttp3.Dispatcher` clash under star imports (this broke the probe); OkHttp's own tests write `mockwebserver3.Dispatcher` in full.

### F4. Forcing a new connection (measured)

A response that carries `Connection: close` makes OkHttp mark the exchange `noNewExchanges` (`CallServerInterceptor`), so the next call opens a new connection and performs a new lookup. Measured over 10 runs each, resolver counting calls: `Connection: close` header gave a second lookup in 10 of 10; `onResponseEnd(CloseSocket())` gave 0 of 10, because the client reused the pooled connection that the server had already closed and the call failed without any new lookup. A request header cannot be used (the transport refuses a caller's `Connection`). The transport needs no internal eviction hook for the test. `ShutdownConnection` on HTTP/1 behaves as `CloseSocket` and has the same staleness race; OkHttp's own 408 and 503 tests pair it with `Connection: Close` for that reason.

### F5. What `mockwebserver3` writes of a response (documented source + measured)

- The status line is `HTTP/1.1 <code> <reason>`; `code(n)` picks a generic reason (`OK`, `Client Error`, ...), `status("HTTP/1.1 404 Not Found")` sets an exact line.
- Headers are written in builder order as `name: value`. `addHeader` validates; `addHeaderLenient` does not and writes the value as UTF-8 (measured: `café` round-trips with code points 99, 97, 102, 233). The fixture's `HttpHeaders` names are tokens, so lenient add is safe and the only way to replay a UTF-8 value.
- `Builder()` starts with `Content-Length: 0`. `body(...)` calls `setHeader("Content-Length", body.contentLength)`, replacing any earlier `Content-Length`. The constructor `MockResponse(code, headers, body)` is `Builder().code().headers(h).body(body)`, so `headers(h)` replaces the default and `body("")` then writes `Content-Length: 0` over a fixture's own value (measured: a `304` built through the constructor with `Content-Length: 5000000` went out with `0`). A `Content-Length: 3` header with a 6-byte body goes out as `6` (measured).
- A body is written after the headers only when `body` is non-null. With no `body(...)` call nothing follows the headers whatever `Content-Length` says; this is how a `304` or a `HEAD` response declares a length without sending bytes.
- `chunkedBody(...)` removes `Content-Length`, adds `Transfer-encoding: chunked` and frames the bytes. A `Transfer-Encoding: chunked` header combined with a raw body is **not** framed: the client fails at once (measured `ProtocolException: Expected leading [0-9a-fA-F] character but was 0x68`).
- Failure cases measured: `Content-Encoding: gzip` with a plain body fails in 5 ms (`IOException: ID1ID2`), a real gzip body decodes; a body with neither `Content-Length` nor chunking and no `onResponseEnd(CloseSocket())` hangs until the timeout; `Connection: close` and `Keep-Alive: timeout=1, max=1` as given change reuse but never hang or corrupt; duplicate `Set-Cookie` lines are kept.
- `204` and `205`: OkHttp throws `ProtocolException: HTTP 204 had non-zero Content-Length: 5` when the header is non-zero (measured and in `CallServerInterceptor`); `Content-Length: 0`, and no header at all, are accepted. `100` as the final response makes the client wait for another response and time out (measured 1012 ms; `CallServerInterceptor` ignores `100` and `102..199`); `101` is returned as a response.
- A response to `HEAD` that carries a body corrupts the connection (measured: the next request on it failed with `ProtocolException: Unexpected status line: BODYBYTESHTTP/1.1 200 OK`). The queue dispatcher cannot see the request method, so the script author chooses the shape per queued response.
- After a `304` that declares `Content-Length: 5000000` and sends nothing, the connection is not reused (measured: the next request used `connectionIndex` 1) and the call took about 110 ms; both are the existing `http-transport.md` F6 figures.
- The reason phrase of the fixture format is in the fixtures' own `HttpMessageCodec.reasonPhrase(status)`.

### F6. `close()` lets the JVM exit: child JVM versus thread check (measured + documented)

**What the transport can leave behind.** OkHttp's `Dispatcher.executorService` is a `ThreadPoolExecutor(0, Int.MAX_VALUE, 60, SECONDS, SynchronousQueue(), threadFactory("$okHttpName Dispatcher", false))`: non-daemon threads named `OkHttp Dispatcher`, idle life 60 s. The shared `TaskRunner.INSTANCE` (connection-pool cleanup, `Okio Watchdog`) is created with daemon threads. Measured with an `enqueue`d call (a synchronous `execute` starts no dispatcher thread): the non-daemon threads were `OkHttp Dispatcher` plus the test server's own `MockWebServer ...` threads; after `dispatcher.executorService.shutdown()` the `OkHttp Dispatcher` thread was gone within 0 ms (the poll loop saw it absent on its first check).

**Child JVM (recommended).** Measured inside a Gradle 9.7.1 test worker (JDK 23):

- `java.class.path` holds `gradle-worker.jar` first and then the whole test runtime classpath (18 entries for the probe: test and main class directories, every dependency); `ClassLoader.getSystemClassLoader()` is the application class loader. The child can therefore be started with `-cp <java.class.path>` and a main class that lives in `jvmTest` (a `@JvmStatic fun main` in an `object`).
- `System.getProperty("java.home")` is the running JDK (it equals the directory of `ProcessHandle.current().info().command()`); `Path.of(java.home, "bin", "java")` started the child on Windows without an `.exe` suffix. `ProcessHandle...command()` can be empty on some systems; `java.home` is always set.
- The child started its own server, made one `enqueue`d call, then: shutting down the dispatcher and evicting the pool exited in 383 ms and 367 ms (two runs); only `evictAll` (no `ExecutorService` shutdown) was still running after 12 s; no cleanup at all was still running after 12 s. The 61 s linger of `http-transport.md` F9 is the failure this detects.
- Design: parent waits `process.waitFor(20, SECONDS)`; on timeout it `destroyForcibly()` and fails with a message saying the transport kept the JVM alive; success requires exit value 0. The child calls `exitProcess(2)` only when its call failed (never on success, because that would mask the linger). The child's output goes to `ProcessBuilder.Redirect.DISCARD` (Java 9+) or a temp file, never an unread pipe.
- Cost: about 0.4 s of JVM start on a warm developer machine for a small class path; the 20 s budget is 50 times that and a fifth of the linger it must detect.

**Thread check (rejected as the primary check).** A snapshot-and-diff of non-daemon threads must exclude `MockWebServer ...` threads (non-daemon, alive until the server is closed), tolerates only a poll because pool threads exit asynchronously after `shutdown()`, depends on the name `OkHttp Dispatcher` or on a diff that any other test's thread (or a later transport thread, for example from the response cache or budget) pollutes, and proves only that no extra thread was left, not that the JVM can exit. It would be a useful cheap Level 2 check for a sibling concern but does not replace the child JVM.

### F7. `webtoolsUrl(path)`: which host (documented + measured)

- `MockWebServer.start()` (no address) calls `start(InetAddress.getByName("localhost"), port)`. The `InetAddress` it binds keeps the name `localhost`, so `hostName` and `url()` print `localhost` with no reverse lookup (measured: `localhost/127.0.0.1:<port>`, `url=http://localhost:<port>/x`). With the default `java.net.preferIPv6Addresses=false` the IPv4 address comes first, so `localhost` binds `127.0.0.1` (measured on Windows 11, which lists both `127.0.0.1` and `::1` for `localhost`).
- `start(InetAddress, port)` with an address built from bytes or a literal has no name; `hostName` then calls `getHostName()`, "a reverse name lookup will be performed" per the Javadoc. Measured on the probe machine: 6 ms, result the literal `127.0.0.1`; but the result is whatever the machine's name service says, so a mapped name can come back (for example a host-file alias), which the relaxation does not admit: the relaxation exempts exactly `localhost`, `127.0.0.1` and `::1` from the port rule. `url()` goes through the same `hostName`. The IPv6 literal bound with `start(InetAddress.getByName("::1"), 0)` prints `hostName` as `0:0:0:0:0:0:0:1` and `url()` as `http://[::1]:<port>/x` (measured).
- `socketAddress.address.hostAddress` is `127.0.0.1` for IPv4 and the expanded `0:0:0:0:0:0:0:1` for `::1` (measured; a link-local address would carry `%scope`). The module's `Url.parse` canonicalises `[0:0:0:0:0:0:0:1]` to host `::1` (the existing `UrlIpv6DeterministicTest` asserts exactly that), which is the form `LOOPBACK_HOSTS` holds, so the expanded text is admitted.
- An IP literal skips the resolver entirely (existing finding `http-transport.md` F4). That is an advantage (no `Dns` call, no reverse lookup, no `localhost` ordering surprise between `::1` and `127.0.0.1`) and a limit: a test that wants the resolver exercised must use a name such as `rebind.test` and build its URL by hand.
- `localhost` as the URL host is rejected: it goes through the resolver (and the guarded resolver) on every new connection, may list `::1` before `127.0.0.1` on some systems with the server bound to only one, and a test's resolver-call counts would be polluted.
- Recommended behaviour: `check(address.isLoopbackAddress)` (a wildcard bind such as `0.0.0.0` is not reachable by that name on every OS), scheme `http` only, `require(path.startsWith('/'))`. The scheme of an HTTPS server is private in `MockWebServer` (it is read only inside `url()`, which would also call `hostName`), so an HTTPS test builds its URL from the literal by hand (F9). A server bound to another `127.0.0.0/8` address (for example `127.0.0.2`) gets the address table's exemption but not the port exemption; its KDoc says so.
- Pure formatting (`InetAddress`, port, path to URL text, IPv6 brackets, scope id removed) is best an `internal` function so a Level 4a test covers it with no socket; the extension then reads the bound address and delegates.

### F8. Proxy settings: an A/B on one URL (measured)

JDK facts: `http.nonProxyHosts` defaults to `localhost|127.*|[::1]` ("The default value excludes all common variations of the loopback address"), so with no override the JVM never proxies a loopback literal. Measured with `http.proxyHost`/`http.proxyPort` pointing at a second `MockWebServer` and the OkHttp client's proxy left `null` (the `Trusted` shape):

| URL | `http.nonProxyHosts` | proxy requests | target requests |
|---|---|---|---|
| `http://127.0.0.1:<port>/` | unset (default) | 0 | 1 |
| `http://origin.test:<port>/` (stub resolver gives `127.0.0.1`) | unset | 1 | 0 |
| `http://127.0.0.1:<port>/` | `""` | 1 | 0 |
| `http://origin.test:<port>/` | `""` | 1 | 0 |

With `Proxy.NO_PROXY` (the `Untrusted` shape) every row sent 0 to the proxy and 1 to the target. The proxy recorded `method=GET`, `target=http://origin.test:<port>/b` (absolute form), `Host: origin.test:<port>`, and `RecordedRequest.url` as the absolute URL.

- **Plain HTTP.** Set `http.proxyHost=127.0.0.1`, `http.proxyPort=<proxy.port>`, `http.nonProxyHosts=""` in a `try/finally` that restores the previous values, in an `@Isolated` class (the existing `GuardedSocketSocksIntegrationTest` does the same). Use the identical URL `target.webtoolsUrl("/p")` for both transports: `Trusted` (via `LoopbackTransports.trusted`) gives proxy 1, target 0; `Untrusted` gives proxy 0, target 1. The proxy server's queue holds one scripted response; the assertion is `proxy.takeRequest(1, SECONDS)?.target` starting with `http://`.
- **HTTPS.** `https.proxyHost`/`https.proxyPort` plus a proxy scripted with `MockResponse(code = 502)`. `Trusted` to `https://127.0.0.1:<closedPort>/`: the proxy records `CONNECT 127.0.0.1:<port> HTTP/1.1` (`method == "CONNECT"`, `target == "127.0.0.1:<port>"`; measured `Unexpected response code for CONNECT: 502` in 7 ms). `Untrusted`: `ConnectException` in about 300 ms and proxy 0 requests. Take `<closedPort>` by binding and closing a `ServerSocket(0)`; do not point the `Untrusted` call at a live plain-HTTP server (a TLS hello to it hangs until the timeout, measured). Do not leave an unrelated response queued on the proxy: a 200 given to a `CONNECT` makes the client start TLS against the mock, which logs a `SEVERE` parse crash (measured) without failing the test.
- **SOCKS.** The existing `GuardedSocketSocksIntegrationTest` technique (a raw `ServerSocket` that counts and closes accepts, `socksProxyHost`, `socksProxyPort`, `socksNonProxyHosts=""`) is the template; `mockwebserver3` is an HTTP server and cannot act as a SOCKS proxy. A plain `OkHttpClient` with `Proxy.NO_PROXY` still reached the SOCKS listener in the probe (the setting is applied at the socket layer), which is exactly why `Untrusted` carries `GuardedSocketFactory`; the transport-level assertion is listener hits 0 for `Untrusted` and at least 1 for `Trusted`.

### F9. HTTPS loopback for the `https` to `http` redirect (documented + measured)

- `MockWebServer.useHttps(SSLSocketFactory)` takes a JDK type. `okhttp-tls` 5.5.0 supplies the certificates: `HeldCertificate.Builder().addSubjectAlternativeName("127.0.0.1").build()` (the SAN may be "a literal hostname, a literal IP address, or a hostname pattern"), `HandshakeCertificates.Builder().heldCertificate(held).build()` for the server (`.sslSocketFactory()`), and `HandshakeCertificates.Builder().addTrustedCertificate(held.certificate).build()` for the client (`.sslSocketFactory()`, `.trustManager`).
- Measured: server on `127.0.0.1` with `useHttps`, a client built from `OkHttpClient.Builder().sslSocketFactory(clientCerts.sslSocketFactory(), clientCerts.trustManager).build()` and then `donor.newBuilder().retryOnConnectionFailure(false).followRedirects(false).followSslRedirects(false).dispatcher(Dispatcher()).connectionPool(ConnectionPool()).build()` reached `https://127.0.0.1:<port>/up`, received a `302` with `Location: http://127.0.0.1:<plain port>/down`, TLS 1.3, and the plain server saw 0 requests (the redirect not followed by the client). Without trust: `SSLHandshakeException`. So a derived client keeps the donor's TLS trust (existing finding `http-transport.md` F9), and the donor is the carrier: build the internal constructor directly from `jvmTest` (the tests see main's and the fixtures' `internal` through the compilation association) with `UrlGuard(policy, GuardRelaxation.LoopbackForTests)`, a stub `Dns` and this donor.
- The server negotiates HTTP/2 by ALPN when the client offers it (measured `protocol=HTTP/2`). Pin `server.protocols = listOf(Protocol.HTTP_1_1)` so the test stays on the wire protocol the other Level 3 tests use, unless the test is about HTTP/2.
- The hop to `http://127.0.0.1:<plain port>/` is a downgrade; with the default settings (`allowHttpsToHttp = false`) the policy refuses it, and a settings override is the positive control. The decision is the policy's, not this file's.
- `okhttp-tls` 5.5.0: POM dependencies `kotlin-stdlib` 2.1.21, `okio-jvm` 3.18.1 (compile), `okhttp-jvm` 5.5.0 (runtime); class files major version 52 (Java 8, measured on the jar), so it loads on a Java 11 test JVM; no BouncyCastle. Add it as `jvmTest` `implementation("com.squareup.okhttp3:okhttp-tls:5.5.0")` in the module's `kotlin.sourceSets`. It is not in the fixtures' dependency list, so the publication check is unaffected, and `verifyJavaFloor` scans only main and the fixtures.
- **JDK-only alternatives, rejected.** (a) `keytool -genkeypair -ext san=ip:127.0.0.1` through `ProcessBuilder` and a `KeyStore`/`SSLContext` set-up: about 30 lines, a process per run, and a platform-dependent tool path. (b) A committed PKCS12 keystore with a private key: a binary secret-shaped file in the repository that expires. (c) `sun.security.x509`: not part of the Java 11 API under `-Xjdk-release=11`. `okhttp-tls` is one line and in-process.

### F10. The Kotlin shape of the four fixtures (documented guidance + judgement)

- `LoopbackTransports` as an `object` of two factories is the name the work fixes. It is a namespace for two related factories, not a utility grab-bag; its call sites read `LoopbackTransports.untrusted("ua")`.
- Parameters: `userAgent: String`, then a whole policy with a default (`OutboundUrlPolicy.Untrusted` / `OutboundUrlPolicy.Trusted` types, so a wrong policy kind does not compile), then `resolve` last. A trailing lambda binds to the last parameter, so `untrusted("ua") { listOf(loopback) }` skips `policy`. Kotlin's conventions: "Prefer declaring functions with default parameter values to declaring overloaded functions."
- Resolver type: `(host: String) -> List<InetAddress>`. Reasons: a single-method contract the caller writes inline needs a function type (the Kotlin guide: "If your API needs to accept a function (any function) with some specific parameter and return types – use a simple functional type"); a `fun interface` adds a public named type to a source-compatible surface for nothing; `okhttp3.Dns` would put an OkHttp type into the fixtures' public signature. The default `{ InetAddress.getAllByName(it).toList() }` is the system resolver; a literal host never reaches it. The resolver may throw `UnknownHostException`, which the transport maps as a DNS failure, and its exceptions propagate unchanged (as `StubDns` in `jvmTest` already does). Two public uses do not justify a public `typealias`.
- Return type `OkHttpTransport` (public, final) rather than `HttpTransport`: the consumer gets the concrete type and `AutoCloseable` either way, and nothing is hidden. KDoc states that the caller closes it.
- `trusted` forces cleartext without touching a caller's other settings: `val effective = if (policy.allowCleartext) policy else OutboundUrlPolicy.trusted(policy) { allowCleartext = true }` (the public `trusted(from, configure)` overload exists).
- `webtoolsUrl` throws `IllegalArgumentException` for a bad path and `IllegalStateException` for a non-loopback bind: these are preconditions of test code, not expected failures, so `Result` is not apt (the repository uses `Result` for expected failures of the production API).
- Extensions on `MockWebServer` suit types the fixtures do not own. Constructs that would be cargo-culted here: a JUnit extension or `@StartStop` (does not close on Jupiter 5.10.1), `runTest` (real I/O under a virtual clock, existing finding `test-support-and-time.md` F3), a fixtures DSL builder (the policy already has one), a public `Resolver` type, `lateinit` servers shared across threads.

## How comparable projects do it

- **OkHttp's own `CallTest`** (tag `parent-5.5.0`, `okhttp/src/jvmTest/kotlin/okhttp3/CallTest.kt`): the stale connection with no retry is `noRecoverWhenRetryOnConnectionFailureIsFalse` (seed response, `MockResponse.Builder().onResponseStart(CloseSocket()).build()`, then `"unreachable!"` with the comment "If this succeeds, too many requests were made."); a `408` is scripted as `code(408)`, `addHeader("Connection","Close")`, `onResponseEnd(ShutdownConnection)` in `getClientRequestTimeout`; a `503` with `Retry-After: 0` the same way in `retryOnUnavailableWith0RetryAfter`; throttled reads in `cancelBeforeBodyIsRead` (`throttleBody(1, 750, MILLISECONDS)`, `requestCount` asserted 1); custom `QueueDispatcher` overrides in `recoverWhenRetryOnConnectionFailureIsTrue`; `exchangeIndex`/`connectionIndex` to prove reuse in several tests. The suite uses the `MockWebServer` extension of its own JUnit rule, which this module cannot (F2 of `test-support-and-time.md`).
- **OkHttp's `CallServerInterceptor`** is the evidence for the framing rules: 204/205 with a non-zero `Content-Length` is a `ProtocolException`; `100` and `102..199` are skipped while the client waits for the real response.
- **`mockwebserver3` `SocketEffect`** replaced `SocketPolicy` in 5.x: a sealed interface with `CloseSocket(closeSocket, shutdownInput, shutdownOutput)`, `ShutdownConnection`, `CloseStream(http2ErrorCode)` and `Stall`, attached at five points (`onRequestStart`, `onRequestBody`, `onResponseStart`, `onResponseBody`, `onResponseEnd`). The old `DISCONNECT_AFTER_REQUEST` is `onResponseStart(CloseSocket())`; `NO_RESPONSE` is `onResponseStart(Stall)`.
- **Retrofit and Coil** parse bodies inside the callback for the cancellation reason in `http-transport.md` F5; the cancel-during-body test is that finding's measurement turned into an assertion on the server side.

## Pitfalls and regrets

- **A blocking latch inside `runBlocking` deadlocks the call it waits for.** `async { transport.execute(...) }` in `runBlocking` runs on the event-loop thread; a `latch.await()` on that thread starves it. Wait with `withContext(Dispatchers.IO) { latch.await(...) }` or `runInterruptible(Dispatchers.IO)`, or poll with `delay`.
- **`hostName` and `url()` are not stable names.** Use the bound address (F7).
- **`SocketEffect.CloseSocket` on `onResponseEnd` is a race, not a way to force a new connection** (F4). The same effect on `onResponseStart` is deterministic because the server has already read the request.
- **`requestCount` is an exact count of requests read, not of requests answered.** A script that uses `onRequestStart` effects inflates it (F1).
- **`enqueue(response)` on a server whose dispatcher was replaced throws `ClassCastException`** (`(dispatcher as QueueDispatcher)`), measured; the KDoc even says so. After `server.dispatcher = ...` script only through the dispatcher.
- **A `HEAD` answered with a body poisons the connection;** a `304` or a `HEAD` answered with a `Content-Length` and no body is correct. For a `GET` the reverse holds: a declared length that is not sent makes the client wait until its timeout (the early-refusal cap test relies on that on purpose).
- **Don't give a `CONNECT` a `200` from a plain mock.** The client then speaks TLS to it and the server logs a parse crash.
- **`.local`, `.internal`, `.localhost` and the other reserved suffixes are refused by name** (`HostRules`); the stub names used here (`second.test`, `rebind.test`, `mixed.test`, `origin.test`) are not.
- **Don't test IPv6 loopback in the default suite.** Binding `::1` worked on the probe machine, but containers without IPv6 cannot bind it; cover the bracket formatting with a pure test and, if wanted, an assumption-guarded server test.
- **A 1 s call timeout is a floor, not a tolerance.** Timing assertions (drip, headers delay) assert an upper bound several times the limit and a lower bound of most of it, never equality; they run on a loaded CI machine.
- **JVM-wide properties** (`http.proxyHost`, `https.proxyHost`, `http.nonProxyHosts`, `socksProxyHost`) are process state: set in `try/finally` in an `@Isolated` class, restore to the previous value or clear when it was unset.
- **`MockWebServer` threads are non-daemon.** A test that skips `close()` keeps the Gradle test JVM alive; close in `@AfterTest` in reverse start order and close the transport before the servers it talks to.
- **Probe-only caveat on Kotlin imports:** `mockwebserver3.*` plus `okhttp3.*` makes `Dispatcher` ambiguous.

## Recommendation for this repository

**The fixtures** (package `com.spartanlabs.webtools.http.testing`, each public declaration with explicit visibility and KDoc; signatures only, behaviour as stated):

```kotlin
public object LoopbackTransports {
    public fun untrusted(
        userAgent: String,
        policy: OutboundUrlPolicy.Untrusted = OutboundUrlPolicy.untrusted(),
        resolve: (host: String) -> List<InetAddress> = { InetAddress.getAllByName(it).toList() },
    ): OkHttpTransport   // internal constructor; UrlGuard(policy, GuardRelaxation.LoopbackForTests); Dns { resolve(it) }

    public fun trusted(
        userAgent: String,
        policy: OutboundUrlPolicy.Trusted = OutboundUrlPolicy.trusted(),
        resolve: (host: String) -> List<InetAddress> = { InetAddress.getAllByName(it).toList() },
    ): OkHttpTransport   // allowCleartext forced true, other settings kept; UrlGuard(effective, GuardRelaxation.None)
}

public fun MockWebServer.webtoolsUrl(path: String = "/"): Url
public fun Fixture.toMockResponse(method: HttpMethod = HttpMethod.Get): MockResponse
public fun MockWebServer.enqueue(fixture: Fixture, method: HttpMethod = HttpMethod.Get)
```

- **`webtoolsUrl`:** `require(path.startsWith('/'))`; `check(socketAddress.address.isLoopbackAddress)`; host is `hostAddress` (IPv6 bracketed, text after `%` removed); text `http://<host>:<port><path>`; `Url.parse(text).getOrThrow()`. Never `hostName`/`url()`. KDoc: the literal bypasses the resolver; an HTTPS server's URL is built by hand.
- **`toMockResponse(method)`**, written with `MockResponse.Builder`, `clearHeaders()` first (the default `Content-Length: 0` must go):
  1. `require(status !in 100..199)`; message says a `1xx` cannot be the final response.
  2. `status("HTTP/1.1 $status ${HttpMessageCodec.reasonPhrase(status)}")`; headers in order with `addHeaderLenient`, **skipping `Content-Length` and `Transfer-Encoding`** (remember whether each was present and the `Content-Length` value).
  3. `204`/`205`: require an empty body, write no body and no `Content-Length`.
  4. `304`, or `method == HttpMethod.Head`: write no body; `Content-Length` is the fixture's own value when present, else the body size for `HEAD`, else none.
  5. Otherwise a fixture that had `Transfer-Encoding` gets `chunkedBody(Buffer().write(body))` (the body bytes are the decoded entity, matching `Fixture.toResponse`); anything else gets `body(Buffer().write(body))`, which sets `Content-Length` from the bytes (an empty body gives `0`).
  6. `Content-Encoding`, `Connection`, `Keep-Alive`, `Set-Cookie` and every other header are written as given; the KDoc states that a fixture carrying `Content-Encoding: gzip` must hold encoded bytes (a mismatch fails fast, never hangs).
- **`enqueue(fixture, method)`:** `check(dispatcher is QueueDispatcher) { "enqueue(fixture) needs the default queue dispatcher; this server has a custom one" }`, then `enqueue(fixture.toMockResponse(method))`.
- **`LoopbackTransports`:** as above. KDoc on both: the caller closes the result; `untrusted` keeps every rule except the loopback ones; with a literal URL the resolver is not consulted; a stub that returns an address is built with `InetAddress.getByAddress(bytes)` or a literal (no lookup), never `InetAddress.getByName("some.name")`.
- **Fixture tests:** a Level 2 test of `toMockResponse` on the status table above (204 without `Content-Length`; 304 keeps a declared length and writes no body; `HEAD`; `Transfer-Encoding`; UTF-8 header value; 1xx refused) asserting the built `MockResponse` (`headers`, `body`), plus a Level 3 round trip through a real `OkHttpClient` for the shapes that can hang; a Level 4a test of the URL text function (IPv4, IPv6 expanded and compressed, scope id, path) with no socket; a Level 2 test that `enqueue(fixture)` fails clearly with a custom dispatcher.

**The tests.**

- Layout: one scenario group per class under `com.spartanlabs.testing.integration.webtools.http` (and `...nonfunctional...` for 4c), a small test-support class (in `testing.support`) that starts servers on `127.0.0.1` through `start()`, tracks them and closes everything in reverse order in `@AfterTest` (each close inside `runCatching` so one failure does not leak the others), the stub resolver `StubDns` (the existing one) adapted to the function type, and the endless-body class of F3 in its own file. Every call under `runBlocking { withTimeout(30.seconds) { ... } }`.
- Use the scripts of F2 and F3 as given. Prefer `requestCount` for "no more requests", `takeRequest(1, SECONDS)` (non-null) for header assertions, and `connectionIndex`/`exchangeIndex` where reuse is part of the precondition.
- JVM exit: a `testing.support` main (`ChildExitMain`) plus the parent test of F6, `@Isolated` not required.
- Proxy properties: one `@Isolated` class for `http.proxyHost`/`https.proxyHost`, and a second for `socksProxyHost` reusing the existing raw-socket listener pattern.
- HTTPS: `okhttp-tls` in `jvmTest`; the single test builds the internal constructor with a donor.
- Why the obvious alternatives lose: `Dispatcher`-per-scenario for everything would hide queue misuse behind blocking; `localhost` as the URL host adds resolver and ordering variables to every test; the thread check does not prove JVM exit; `@StartStop` does not close servers on the pinned Jupiter.

## Gaps

- **Not measured on Linux or macOS.** Everything measured ran on Windows 11 with JDK 23. The claims that carry the cross-OS requirement are from source and the JDK documents: `start()` binds `localhost` (IPv4 first by default), `webtoolsUrl` uses the bound literal, `java.home` plus `java.class.path` for the child JVM, `Path.of(java.home, "bin", "java")`. The child-JVM launch on macOS and Linux and the JDK 17 and 26 ends of the build range are unverified. The hosts-file reverse-lookup alias (F7) is a documented possibility that no source I found demonstrates; the recommendation does not depend on it.
- **The transport is not built.** Every scenario was measured against a plain `OkHttpClient` configured as the design describes, not against `OkHttpTransport`. The failure names in the assertions (`Io`, `Timeout`, `BodyTooLarge`, `TooManyRedirects`, `RefusedByPolicy`, `Closed`) follow the port's contract in the work's description; which `TransportFailure` leaf the stale-connection case maps to, how a `Connection: close` interacts with the `ExchangeGuard` counter, and how `close()` completes calls mid-body are left to the failure-surface work.
- **The `https` to `http` outcome** (refused, returned as the `3xx`, or followed) is the redirect decision table's and the policy's; F9 gives only the mechanics. Likewise whether `allowHttpsToHttp` appears in `settings { }` exactly as written is read from `TransportSettings`, not run.
- **`toMockResponse(method)` and `enqueue(fixture, method)` add a `HttpMethod` parameter** beyond the four signatures the work names, to replay a recorded `HEAD` fixture faithfully; the alternative is to leave `HEAD` to hand-built responses and document it. Their exact form is a design choice, not a measured fact. The `1xx` refusal and the empty-body requirement for `204` are stricter than `Fixture` itself (which accepts both); a fixture-format rule would remove the asymmetry.
- **The prototype of `toMockResponse` was run on a stand-in class**, not on `Fixture`/`HttpHeaders`; the header-copy loop over `HttpHeaders.entries()` and the use of `HttpMessageCodec.reasonPhrase` (internal to the fixtures) were read, not compiled.
- **IPv6 loopback and `127.0.0.2` binds** were not tested beyond `::1` on Windows; macOS has no `127.0.0.2` by default (documented practice, not re-verified here), which is why the hop-2-refused script avoids it.
- **No Level 3 run under `runBlocking` against the real transport**, so timing bounds (the 1 s drip, 20 s child-JVM budget) are starting values to confirm on the three operating systems in CI.
