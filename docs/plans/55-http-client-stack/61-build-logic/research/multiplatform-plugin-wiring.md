# Wiring binary-compatibility-validator 0.18.2 and vanniktech 0.36.0 into the multiplatform convention plugin

## Question

How should `webtools.kotlin-multiplatform-library` (a precompiled script plugin in the included `build-logic` build, `jvm()` target only) apply binary-compatibility-validator 0.18.2 and configure vanniktech `maven-publish` 0.36.0, and how should the shared `webtools.published-library` configure vanniktech so that the three Kotlin/JVM modules keep publishing exactly what they publish today?

Requirements an answer must meet: one JVM dump per multiplatform module with `apiCheck` in `check`; no dump and no behaviour change for `webtools-udp`, `webtools-scraping`, `webtools-browser`; Gradle 9.7.1, KGP 2.2.0, configuration cache on, Windows with Oracle JDK 23; plugin-marker dependencies with literal versions on `build-logic`'s classpath and plugins applied by id with no version; a sources jar plus an empty javadoc jar on every multiplatform publication.

## Bottom line

- **Apply binary-compatibility-validator (BCV) in the multiplatform plugin's `plugins {}` block, after `org.jetbrains.kotlin.multiplatform`, with no `apiValidation {}` configuration at all.** From a leaf project, `allprojects {}` touches only that project. The defaults already are what the design wants: dump directory `api`, KLib validation off, validation enabled. A `jvm()`-only module gets `apiDump`, `apiCheck`, `jvmApiBuild`, `jvmApiDump`, `jvmApiCheck`, writes `<module>/api/<project-name>.api`, and `check` depends on `apiCheck`. Do not apply it to the root or to a parent project: a second application on the same subtree fails with "Cannot add a configuration with name 'bcv-rt-jvm-cp'".
- **BCV 0.18.2 cannot read Java 23 class files, which is what the build produces until the Java 11 floor lands.** It hard-codes `org.ow2.asm:asm:9.6` / `asm-tree:9.6` as the runtime classpath of its worker, and ASM 9.6's `ClassReader` throws `Unsupported class file major version 67` (reproduced here with the 9.6 jar on this JDK 23.0.2; ASM 9.8 reads the same class). GeneralTools hit the same failure on this host with this BCV version. Fix inside the plugin, without `afterEvaluate`: add `org.ow2.asm:asm:9.8` and `asm-tree:9.8` to BCV's own `bcv-rt-jvm-cp` configuration. Without it, `apiDump` fails for any module that has at least one class, and so does the TestKit test.
- **`apiCheck` fails when no dump exists** (`Expected file with API declarations 'api/<name>.api' does not exist.` plus a hint to run `:apiDump`), and so does `check`/`build`. The first multiplatform module must commit its dump (generated by `apiDump`) with its first public declaration. A module with no public API dumps a zero-byte file and `apiCheck` passes against a zero-byte file. The TestKit test must run `apiCheck` first (expect the failure), then `apiDump`, then `apiCheck` (expect success), and check `check`'s dependency on `apiCheck` without needing a dump.
- **vanniktech: call `publishToMavenCentral()` and `signAllPublications()` from `webtools.published-library` through the typed `mavenPublishing {}` accessor, and do not call `configure(...)` there.** With no Gradle properties set, the full plugin does nothing else (Central publishing, signing and every `POM_*` property default to off). Its own `afterEvaluate` calls `configureBasedOnAppliedPlugins()`, which for `org.jetbrains.kotlin.jvm` picks `KotlinJvm(JavadocJar.Javadoc(), SourcesJar.Sources())`, which is what today's root block gets. An explicit `configure(KotlinJvm())` would silently switch the three modules to an empty javadoc jar in 0.36.0, so do not "make it explicit" without passing `JavadocJar.Javadoc()`.
- **In the multiplatform plugin call `configure(KotlinMultiplatform(javadocJar = JavadocJar.Empty(), sourcesJar = SourcesJar.Sources()))` in the script body** (the Kotlin plugin is already applied by `plugins {}`). It equals the auto-detected choice today and pins it against the Dokka auto-switch. Plugin application order does not matter to vanniktech or to BCV; both use retroactive `withId`/`withPlugin` hooks.
- **Kotlin plugin markers vs `kotlin-gradle-plugin`:** both resolve to the same single jar (each marker POM has exactly one dependency, `kotlin-gradle-plugin:2.2.0`), the plugin ids resolve from that jar either way, and every marker exists on Maven Central. Keep the markers: they keep the repository's convention, state which plugin ids the scripts apply, and match MyGameTools. The full artifact is the equally valid, shorter alternative (Ktor and Okio use it).

## Findings

Evidence tiers: **source-read** (code at a pinned tag), **measured** (run by the researcher outside the repository, no Gradle), **recorded** (this organisation's own record of a run), **common practice** (mature projects visibly do it).

### F1. BCV 0.18.2 identity and currency — source-read, common practice

- Plugin id `org.jetbrains.kotlinx.binary-compatibility-validator`; the `0.18.2` jar also carries the legacy id `binary-compatibility-validator` (`META-INF/gradle-plugins/*.properties` both present). Marker coordinates: `org.jetbrains.kotlinx.binary-compatibility-validator:org.jetbrains.kotlinx.binary-compatibility-validator.gradle.plugin:0.18.2`, whose single dependency is `org.jetbrains.kotlinx:binary-compatibility-validator:0.18.2`. Both exist on Maven Central (HTTP 200 on the POMs); the Plugin Portal answers the marker with a redirect. The jar's Gradle module metadata declares one runtime dependency, `java-diff-utils:4.12`; KGP is `compileOnly` and comes from the same classloader.
- 0.18.2 (released 2026-09-02) is the latest release; its only change is "Prevent configuration crash on hosts unrecognized by Kotlin/Native". The README states the plugin "is in maintenance mode" and that new features go to "the experimental binary compatibility validation in the Kotlin Gradle plugin". Requirements stated: Gradle 6.1.1+, Kotlin 1.6.20+.
- Because the plugin casts `extensions.getByName("kotlin") as KotlinMultiplatformExtension`, it needs the same classloader as KGP. Applying it from a precompiled script plugin, where both sit on `build-logic`'s one classpath, satisfies that. The code comments on the split-classloader case ("the BCV and the Kotlin plugins may be located in different class loaders").

### F2. What `apply` touches when applied to one leaf project — source-read

`BinaryCompatibilityValidatorPlugin.apply` creates the `apiValidation` extension on the applying project, registers an `afterEvaluate` check on `ignoredProjects`, then runs `allprojects { configureProject(it, extension) }`. On a leaf project `allprojects` is the project itself, so nothing else is touched. `configureProject` creates the configurations `bcv-rt-jvm-cp` and `bcv-rt-jvm-cp-resolver`, then registers three `withPlugin` hooks (`kotlin`, `kotlin-android`, `kotlin-multiplatform`); each fires immediately if the plugin is already applied and later otherwise, so order is irrelevant. Upstream's own functional tests cover "plugin on a sub-project" (`SubprojectsWithPluginOnSubTests`).

### F3. Defaults of `apiValidation` — source-read

`ApiValidationExtension`: `validationDisabled = false`, `apiDumpDirectory = "api"`, empty `ignoredProjects`/`ignoredPackages`/`ignoredClasses`/`nonPublicMarkers`/`publicMarkers`, and `klib.enabled = false` (`@ExperimentalBCVApi`; touching `klib {}` requires an opt-in, so leaving it alone avoids that). `apiDumpDirectory` must resolve inside the project directory or configuration throws.

### F4. Tasks, dump path and `check` wiring for a `jvm()`-only project — source-read plus upstream functional tests

- In the `kotlin-multiplatform` hook: `apiDump` (group `other`) and `apiCheck` (group `verification`) are registered; `check` is made to depend on `apiCheck`. For each JVM-based target, `<target>ApiBuild` (hidden, no group), `<target>ApiCheck` and `<target>ApiDump` are registered on the `main` compilation, so for target `jvm`: `jvmApiBuild`, `jvmApiCheck`, `jvmApiDump`. `apiCheck` depends on `jvmApiCheck`; `apiDump` on `jvmApiDump`.
- Directory: with exactly one JVM-based target (`KotlinPlatformType.jvm` or `androidJvm`) the dump sits in the common directory, `<projectDir>/api/<project.name>.api`; with two or more it becomes `api/<target>/<project.name>.api`. The file name is the Gradle project name, not the artifact id and not a configurable value, so it is the leaf project's directory name in the real build and `rootProject.name` in a generated TestKit project. Adding a second JVM target later moves the dump.
- Only the `main` compilation is dumped (`mainCompilationOrNull`), so a hand-declared test-fixtures compilation is not part of the dump.
- KLib tasks (`klibApiDump`, `klibApiCheck`, `klibApiMerge`, `klibApiMergeInferred`, `klibApiExtractForValidation`) are also registered and made dependencies of `apiDump`/`apiCheck`, but `isEnabled` is `false` while `klib.enabled` is false, so they report SKIPPED. Expect them in task output and in a `--dry-run` graph.
- Upstream `MultiPlatformSingleJvmTargetTest` runs `:apiCheck`, `:apiDump`, and the empty-project cases against this exact shape (`kotlin("multiplatform")` with a single `jvm` target).

### F5. Missing dump and empty API — source-read plus upstream functional tests

- `KotlinApiCompareTask` throws, when `<dir>/<name>.api` is absent: `Expected file with API declarations '<path relative to the root project dir>' does not exist.` then `Please ensure that ':apiDump' was executed in order to get an API dump to compare the build against`. The path uses the OS separator (upstream's test builds it with `File.separator`); in the real repo it is `webtools-http\api\webtools-http.api` on Windows. `jvmApiCheck` is the failing task and `apiCheck`/`check` are not run (upstream `testApiCheckFailsForEmptyProjectWithoutDumpFile`).
- A mismatch fails with `API check failed for project <name>.` followed by a unified diff and `You can run :<name>:apiDump task to overwrite API declarations`. Comparison is by lines, so CRLF/LF differences do not matter.
- A project with no public declarations: `apiDump` succeeds and writes a zero-byte file; `apiCheck` against a zero-byte file succeeds (upstream `testApiDumpPassesForEmptyProject` and `testApiCheckPassesForEmptyProject`, where the fixture file is created empty).
- `SyncFile` (the `apiDump` task type) deletes the committed dump if the built dump file does not exist, rather than failing.

### F6. What BCV resolves at execution, and so which repositories the module needs — source-read

`bcv-rt-jvm-cp` declares `org.ow2.asm:asm:9.6`, `org.ow2.asm:asm-tree:9.6` and `org.jetbrains.kotlin:kotlin-metadata-jvm:<KGP version>` (the version is read from KGP's `project.properties` resource, with a `2.0.0` fallback when unreadable). It is resolved against the repositories of the module project, in a classloader-isolated worker. All three exist on Maven Central, so `mavenCentral()` in the module is enough. The module's `jvmApiBuild` also takes `jvmMain`'s compile classpath as an input. The KLib counterpart `bcv-rt-klib-cp` declares `kotlin-compiler-embeddable:<KGP version>` for the disabled KLib tasks; whether a configuration-cache store resolves it for those skipped tasks was not established (Gap 3).

### F7. Java 23 class files break BCV 0.18.2's reader — source-read, measured, recorded

- Source: the 9.6 pin is `project.dependencies.add(dependencyConfiguration.name, "org.ow2.asm:asm:9.6")` (and `asm-tree`) in `prepareJvmValidationClasspath`, unchanged on `master`. The reader is `ClassReader(stream).accept(classNode, ClassReader.SKIP_CODE)`, which uses the default constructor that checks the class version. BCV's own `libs.versions.toml` uses ASM 9.8, but only for its compile and test classpaths; that is why its test suite does not see this.
- ASM 9.6's `ClassReader` rejects anything above `Opcodes.V22` (66). The ASM release list gives `V23` as new in ASM 9.7 (2024-03-23).
- Measured here (JDK 23.0.2): reading `java/lang/Object.class` (major 67) with `asm-9.6.jar` throws `IllegalArgumentException: Unsupported class file major version 67`; with `asm-9.8.jar` it succeeds.
- Recorded: GeneralTools' `final-implementation.md` (repository at `7e171ab`) records that on this host with Oracle JDK 23.0.2 "the first run ... failed in `:apiBuild` with `Unsupported class file major version 67`" with BCV 0.18.2 and KGP 2.2.0, and that the dump was produced under JDK 17 instead.
- Consequence for WebTools: until the Java 11 floor makes `main` compile to major 55, a multiplatform module compiled on this host emits major 67, so `apiDump` (and `apiCheck`) fail for any module with at least one class. The explicit `TargetJvmVersion` attribute does not change the bytecode. After the floor lands, 9.6 suffices, and the override becomes harmless.
- The override is a plain dependency declaration, because the configuration is created eagerly in `apply` and Gradle resolves the conflict to the highest version. BCV's own build compiles and tests against ASM 9.8, so the combination is the one upstream exercises.

### F8. Configuration cache and Gradle 9 — source-read, common practice

- Source: the task classes read `project` only in field initialisers (`project.objects.fileProperty()`, `project.name`, `project.rootDir`, the extension object), never in `@TaskAction` bodies; `buildDir`, `convention` and `Project.properties` are not used (a 2025 change, #287, replaced `getProperties` with `findProperty`). Upstream's functional-test runner adds `--configuration-cache` to every build by default.
- Upstream CI wraps Gradle 8.5 and its compatibility tests cover 6.1.1, 7.0 and 8.0, so Gradle 9.x is not in upstream's matrix. In the wild: kotlinx.serialization `master` (`4c28c3e`) runs Gradle 9.7.1 with BCV 0.18.1; Okio `master` (`334c028`) runs Gradle 9.8.1 with BCV 0.18.2 applied through the marker coordinates; kotlinx-datetime runs Gradle 9.6.1 with BCV 0.17.0. The tracker has no open or closed issue about Gradle 9 or the configuration cache on JVM targets; the open Gradle-9-era issues (#312, #315) concern AGP 9 (Android). Project Isolation is not supported (#298, closed as not relevant to the migrated plugin); that is not required here.
- Nothing in the plugin warns or fails on 9.7.1 by inspection, but no run on 9.7.1 with KGP 2.2.0 was made (Gap 1).

### F9. vanniktech 0.36.0: marker, minimums, call surface — source-read

- Marker `com.vanniktech.maven.publish:com.vanniktech.maven.publish.gradle.plugin:0.36.0` exists on Maven Central; its one dependency is `com.vanniktech:gradle-maven-publish-plugin:0.36.0`. The jar carries ids `com.vanniktech.maven.publish` and `com.vanniktech.maven.publish.base`.
- 0.36.0 (2026-01-18): minimum JDK 17, Gradle 9.0.0, KGP 2.2.0; tested up to Gradle 9.3.0 and KGP 2.3.0. This repository already runs it on Gradle 9.7.1 (root build). 0.37.0 is out (2026-06-21); the design keeps 0.36.0.
- `mavenPublishing { ... }` is the extension `MavenPublishBaseExtension`, so `publishToMavenCentral()` (no-argument form: `automaticRelease` and `validateDeployment` default from Gradle properties) and `signAllPublications()` are plain member calls, valid in a precompiled script plugin exactly as in the root block. `signAllPublications()` sets `required` to `version` not ending in `-SNAPSHOT`, so any `Sign` task of a non-snapshot version fails without keys; a TestKit check that only generates Gradle Module Metadata does not run `Sign`.

### F10. What the full plugin does with Gradle properties that are absent — source-read

`MavenPublishPlugin.apply` applies the base plugin; then calls `publishToMavenCentral(...)` only if `mavenCentralPublishing` is `true` (or legacy `SONATYPE_HOST=CENTRAL_PORTAL`), `signAllPublications()` only if `signAllPublications` or `RELEASE_SIGNING_ENABLED` is `true`; both default to `false` when absent. `pomFromGradleProperties()` runs unconditionally, but each of `GROUP`, `POM_ARTIFACT_ID`, `VERSION_NAME`, `POM_NAME`, `POM_DESCRIPTION`, `POM_URL`, `POM_INCEPTION_YEAR`, `POM_ISSUE_*`, `POM_SCM_*`, `POM_LICENCE_*`/`POM_LICENSE_*`, `POM_DEVELOPER_*` is only applied if present in the project's extra properties. Neither the repository's `gradle.properties` nor the maintainer's user-level `gradle.properties` defines any of them (the latter holds `mavenCentralUsername`, `mavenCentralPassword`, `signing.*` and the configuration-cache switch), so the explicit calls are the only source of Central publishing and signing, as in the root block. Because `pomFromGradleProperties()` is registered before the convention plugin's `pom {}` action, an explicit `pom {}` runs later and wins if a `POM_*` property is ever set.

### F11. What `configureBasedOnAppliedPlugins()` picks — source-read

`MavenPublishPlugin.apply` ends with `project.afterEvaluate { baseExtension.configureBasedOnAppliedPlugins() }` (commented "will no-op if it was already called"); inside, `if (platform.isPresent) return` makes an earlier explicit `configure(...)` win. The `when` order is: `org.jetbrains.kotlin.multiplatform`, `com.android.library`, ..., `com.gradle.plugin-publish`, `java-gradle-plugin`, then `org.jetbrains.kotlin.jvm` → `configure(KotlinJvm(javadocJar, sourcesJar))`, then `java-library`/`java`.

Defaults (`defaultJavaDocOption(true)`): Dokka v2 plugin applied → Dokka javadoc; otherwise **not** multiplatform → `JavadocJar.Javadoc()` (the Gradle `javadoc` task via `plainJavadocJar`); otherwise multiplatform → `JavadocJar.Empty()`. So:

| Module | Auto-detected | What it publishes |
|---|---|---|
| Kotlin/JVM (`webtools-udp` etc.) | `KotlinJvm(Javadoc(), Sources())` | publication `maven` from component `java`, `withSourcesJar()`, `plainJavadocJar` |
| Kotlin Multiplatform | `KotlinMultiplatform(Empty(), Sources(), listOf("release"))` | KGP's own publications, `withSourcesJar(true)`, `empty*JavadocJar` per publication |

The three existing modules therefore publish the same shape as today, because the same plugin makes the same call at the same lifecycle point (`afterEvaluate`) and the Kotlin plugin is applied by then in either arrangement.

The 0.36.0 changelog records a behaviour change that is a trap here: "When calling `configure(...)` manually to configure what to publish and not passing `javadocJar` explicity, the plugin now defaults to publishing an empty javadoc jar." `KotlinJvm`'s constructor default is `JavadocJar.Empty()`, so `configure(KotlinJvm())` differs from auto-detection (`Javadoc()`).

### F12. Does application order of the Kotlin plugin and vanniktech matter? — source-read

No, for the default path. The base plugin's version checks use `plugins.withId` for `org.jetbrains.kotlin.jvm` and `...multiplatform`; `signAllPublications()` uses `withId("org.jetbrains.kotlin.multiplatform")` for the signature-directory workaround; `coordinates(...)` decides on `hasPlugin("org.jetbrains.kotlin.multiplatform")` lazily inside a `configureEach` over publications; and `configureBasedOnAppliedPlugins()` runs in `afterEvaluate`. Only an explicit `configure(KotlinMultiplatform(...))` in a script body needs the Kotlin plugin applied first (it `check`s `hasPlugin`), which the `plugins {}` block order provides. Both plugins must see the same KGP classes (the base plugin casts to `KotlinBasePlugin`); with everything on `build-logic`'s classpath they do, and the existing measurement shows no "loaded multiple times" warning.

### F13. Kotlin plugin markers vs the single artifact — source-read, common practice

- `org.jetbrains.kotlin.jvm:org.jetbrains.kotlin.jvm.gradle.plugin:2.2.0` and `org.jetbrains.kotlin.multiplatform:org.jetbrains.kotlin.multiplatform.gradle.plugin:2.2.0` both exist on Maven Central, and each POM has exactly one dependency, `org.jetbrains.kotlin:kotlin-gradle-plugin:2.2.0`. That artifact's jar contains `META-INF/gradle-plugins/org.jetbrains.kotlin.jvm.properties` and `...multiplatform.properties`.
- Gradle's precompiled-plugin documentation only requires the plugin on the plugin project's implementation classpath, and forbids versions and `apply false` in the scripts. It does not require a marker.
- Trade-off: markers are one line per applied plugin id (two lines resolving to one jar), derive mechanically from the id, and tell a reader which ids the scripts use; the single artifact is one line, covers every Kotlin plugin id, and is what Ktor and Okio use. Both put KGP's classes on the compile classpath of `build-logic` (compile-scope POM dependency). Choose by convention: the markers match MyGameTools and the premise of this design.

## How comparable projects do it

- **avro4k** (`avro-kotlin/avro4k`, default branch read 2026-10-21, `build-logic/src/main/kotlin/library-module-conventions.gradle.kts`): BCV applied per module from a convention plugin — `plugins { kotlin("jvm") ... id("org.jetbrains.kotlinx.binary-compatibility-validator") }` followed by `apiValidation { nonPublicMarkers += ... }`. Its `build-logic/build.gradle.kts` builds the dependency as `"${it.pluginId}:${it.pluginId}.gradle.plugin:${it.version.requiredVersion}"`, i.e. the marker coordinates, for BCV, vanniktech and KGP, declared `compileOnly`. Common practice for the marker form; a JVM module, not multiplatform.
- **akkurate** (`nesk/akkurate`, default branch read 2026-10-21, `buildSrc/src/main/kotlin/akkurate.kmp-library-conventions.gradle.kts`): per-module KMP convention plugin `plugins { id("akkurate.publishing-conventions"); kotlin("multiplatform"); id("org.jetbrains.kotlinx.binary-compatibility-validator") }`, with `apiValidation { klib { enabled = true } }`. Same shape as the recommendation, with KLib on (not wanted here).
- **kotlinx.coroutines 1.10.2** (`build.gradle.kts`): the root-application pattern, `id("org.jetbrains.kotlinx.binary-compatibility-validator") version "0.16.2"` plus `apiValidation { ignoredProjects += unpublished + ... }`. The alternative this design rules out (every subproject is configured; exclusions by name).
- **kotlinx.serialization** (`master` `4c28c3e`): root-level `id("org.jetbrains.kotlinx.binary-compatibility-validator")` with `ignoredProjects.addAll(listOf(...))` and `klib { enabled = true }`, on Gradle 9.7.1 and BCV 0.18.1.
- **Okio 3.18.2** (`okio/build.gradle.kts` at tag `parent-3.18.2`): `configure<MavenPublishBaseExtension> { configure(KotlinMultiplatform(javadocJar = JavadocJar.Empty())) }`, i.e. the explicit call in a module script. Okio's root `build.gradle.kts` (`master`) calls `publishToMavenCentral(automaticRelease = true)`, `signAllPublications()` and `pom {}` for all projects. At `master` `334c028` Okio resolves BCV 0.18.2 through its marker coordinates (`libs.versions.toml`) on Gradle 9.8.1, vanniktech 0.37.0 and KGP through their full artifacts.
- **Ktor 3.6.0** (`build-logic/src/main/kotlin/ktorbuild.publish.gradle.kts`): a precompiled script plugin with `plugins { id("com.vanniktech.maven.publish"); id("signing") }`, `mavenPublishing { publishToMavenCentral(automaticRelease = true); ... pom { ... } }` and signing configured by a helper. This plugin never calls `configure(...)`, so it relies on auto-detection. Its `build-logic/build.gradle.kts` uses `implementation(libs.kotlin.gradlePlugin)` and `implementation(libs.mavenPublishing)`, the full artifacts. Ktor has moved ABI checking to KGP's built-in `abiValidation` (`ktorbuild.compatibility.gradle.kts`).
- **MyGameTools** (this organisation, `build-logic/src/main/kotlin/gametools.published-library.gradle.kts`): `plugins { id("gametools.kotlin-library"); id("org.jetbrains.dokka"); id("com.vanniktech.maven.publish") }` and `mavenPublishing { publishToMavenCentral(); signAllPublications(); configure(JavaLibrary(javadocJar = JavadocJar.Dokka(...), sourcesJar = true)); pom { ... } }`, with marker coordinates for KGP, serialization, vanniktech 0.36.0 and Dokka in `build-logic/build.gradle.kts`. Its `sourcesJar = true` uses the Boolean constructor that 0.36.0 deprecates in favour of `SourcesJar.Sources()`. It has no BCV.
- **GeneralTools** (this organisation): the BCV 0.18.2 / JDK 23 failure above; its current `master` has moved to KGP's built-in `abiValidation()`.

## Pitfalls & regrets

1. **ASM 9.6 vs Java 23 class files** (F7). The failure is in `:jvmApiBuild` and looks like a compiler problem. It reproduces on any module with a class when the build JDK is 23 and no `jvmTarget`/release is set.
2. **Applying BCV on an ancestor and on a leaf** fails with `Cannot add a configuration with name 'bcv-rt-jvm-cp' as a configuration with that name already exists` (issue #275, closed as won't-fix because the plugin is frozen). Per-leaf application only.
3. **The dump name is the Gradle project name.** A generated TestKit project without `rootProject.name` uses a temporary directory name; set it in the generated `settings.gradle.kts`.
4. **A second JVM-based target moves the dump** to `api/jvm/<name>.api`. The convention plugin declares `jvm()` itself, and module scripts must not add `androidTarget`/another `jvm("x")`.
5. **`check` fails on a fresh module** until the dump is committed (F5). The same applies to every public-API change afterwards; the `final-implementation` of the first module should record the first `apiDump`.
6. **`configure(KotlinJvm())` changes published jars** (F11). Auto-detection is what keeps them identical.
7. **Applying BCV from an `afterEvaluate` of our own** is unnecessary and unsafe: `apply` itself calls `afterEvaluate` (for the `ignoredProjects` check), which Gradle rejects on a project that is already evaluated.
8. **`signAllPublications()` makes non-snapshot publishing require keys.** Tests that publish to a file repository need an in-memory key or a `-SNAPSHOT` version (not run here; F9 is source-read).
9. **Applying vanniktech earlier than the module's `version` assignment is harmless.** vanniktech reads `group`, `name` and `version` lazily (`convention(project.provider { project.version.toString() })`), so a module's later `version = "2.0.0a"` still applies when the plugin moves from the root `subprojects {}` block to a plugin applied in `plugins {}`.
10. **BCV is in maintenance mode** (F1): nothing new will be added, ASM will not be fixed in this plugin unless Kotlin's own tooling forces it.

## Recommendation for this repository

Pin all four plugins as marker coordinates in `build-logic/build.gradle.kts` (literal versions), and wire the plugins like this.

```kotlin
// build-logic/build.gradle.kts (dependencies)
implementation("org.jetbrains.kotlin.jvm:org.jetbrains.kotlin.jvm.gradle.plugin:2.2.0")
implementation("org.jetbrains.kotlin.multiplatform:org.jetbrains.kotlin.multiplatform.gradle.plugin:2.2.0")
implementation("com.vanniktech.maven.publish:com.vanniktech.maven.publish.gradle.plugin:0.36.0")
implementation("org.jetbrains.kotlinx.binary-compatibility-validator:org.jetbrains.kotlinx.binary-compatibility-validator.gradle.plugin:0.18.2")
```

```kotlin
// webtools.published-library.gradle.kts
plugins { id("com.vanniktech.maven.publish") }

mavenPublishing {
    publishToMavenCentral()
    signAllPublications()
    pom { /* the shared block of build.gradle.kts:68-90, unchanged */ }
}
// No configure(...): afterEvaluate picks KotlinJvm(Javadoc(), Sources()) for Kotlin/JVM modules.
```

```kotlin
// webtools.kotlin-multiplatform-library.gradle.kts (publishing and ABI part)
import com.vanniktech.maven.publish.JavadocJar
import com.vanniktech.maven.publish.KotlinMultiplatform
import com.vanniktech.maven.publish.SourcesJar

plugins {
    id("org.jetbrains.kotlin.multiplatform")
    id("webtools.published-library")
    id("org.jetbrains.kotlinx.binary-compatibility-validator")
}

kotlin { jvm { /* jvmTarget, -Xjdk-release, TargetJvmVersion: see java-11-floor.md F1 */ } }

// BCV 0.18.2 hard-codes ASM 9.6, which rejects class files above Java 22 (major 66).
dependencies {
    "bcv-rt-jvm-cp"("org.ow2.asm:asm:9.8")
    "bcv-rt-jvm-cp"("org.ow2.asm:asm-tree:9.8")
}

mavenPublishing {
    configure(KotlinMultiplatform(javadocJar = JavadocJar.Empty(), sourcesJar = SourcesJar.Sources()))
}
```

Reasoning: BCV and vanniktech each wire themselves through retroactive hooks, so the plugin needs no `afterEvaluate` and no ordering care beyond listing the Kotlin plugin first; leaving `apiValidation {}` untouched keeps the defaults the design wants and avoids the `@ExperimentalBCVApi` opt-in; leaving `configure(...)` out of the shared plugin is the only arrangement that guarantees the three existing modules' javadoc jars do not change; the explicit multiplatform `configure` pins the intent against a future Dokka plugin. The ASM override is needed for as long as `main` compiles to Java 23 and is harmless afterwards.

Module-side and test-side consequences:

- **The module repositories** must include `mavenCentral()` (BCV's runtime classpath resolves from the module's repositories); the published-library or the language plugin supplies it as today.
- **The first multiplatform module** runs `./gradlew :<module>:apiDump` once it has public declarations, commits `<module>/api/<module>.api` with that change, and re-runs `apiDump` for every public-API change. A module still without public API commits a zero-byte `api/<module>.api` or no dump and no `check` run.
- **The TestKit tests of the plugin** (generated project with `rootProject.name` set, `mavenCentral()` repository, at least one public class, configuration cache on):
  1. `apiCheck` before a dump → build fails in `:jvmApiCheck` with `Expected file with API declarations` and the module-relative path.
  2. `apiDump` → `api/<rootProject.name>.api` exists and contains the public class's `public final class ...` line; `:jvmApiDump` and `:apiDump` succeed.
  3. `apiCheck` → success.
  4. `check --dry-run` lists `:apiCheck` and `:jvmApiCheck` (task names are source-read).
  5. A second `apiDump` run reuses the configuration cache entry.
  Test 2 fails on this host without the ASM override, and that is the regression guard for it; on a build JDK of 22 or lower it passes either way (Gap 2).
- **A Kotlin/JVM module never applies BCV** in this design, so there is no `apiDump` on `webtools-udp`, `webtools-scraping`, `webtools-browser`.

I rejected the root-level application (the pattern kotlinx.coroutines and kotlinx.serialization use) because it configures every subproject including the three that take no dump, and then fails when a leaf also applies the plugin (Pitfall 2). I rejected `configure(KotlinJvm(...))` in the shared plugin for the reason in F11.

## Gaps

**Known gaps**

1. **Nothing was run under Gradle** (this research was read-only). BCV 0.18.2 on Gradle 9.7.1 with KGP 2.2.0 and the configuration cache is supported by inspection, by upstream tests on Gradle 8.5, and by other projects' use on Gradle 9.6-9.8 with BCV 0.17.0-0.18.2, not by a run on this toolchain. The TestKit tests above are the first such run; the exact `--dry-run` task names are source-read.
2. **The ASM override is untested in Gradle.** The ASM 9.6 failure is reproduced against the ASM jar, source-read in BCV, and recorded by GeneralTools; that the added dependencies on `bcv-rt-jvm-cp` resolve to 9.8 and cure it is standard conflict resolution but unmeasured. The regression test is host-JDK dependent: it only proves the override on a JDK 23 (or higher) build host.
3. **Whether a configuration-cache store resolves `kotlin-compiler-embeddable` for the skipped KLib tasks** (`bcv-rt-klib-cp`) was not established. It exists on Central (version equal to KGP); the cost would be an extra download, not a failure.
4. **Accessor availability for `mavenPublishing {}` in a plugin script that gets vanniktech only through another precompiled plugin** (`webtools.published-library`) is measured only for plugin scripts that apply vanniktech themselves (the build-topology findings). If the accessor is not generated, use `extensions.configure<com.vanniktech.maven.publish.MavenPublishBaseExtension>("mavenPublishing") { ... }` or list `id("com.vanniktech.maven.publish")` in the plugin's own `plugins {}` block (idempotent).
5. **No published-jar comparison for the move** was made here; F11 argues identity from the code path (same plugin, same `afterEvaluate` call), and the earlier topology measurement found identical POMs and metadata for the three modules.
6. **BCV's maintenance status** — frozen; KGP's built-in ABI validation replaces it (kotlinlang's page documents `abiValidation()` with `checkKotlinAbi`/`updateKotlinAbi`, marked with `ExperimentalAbiValidation`). Out of scope here; recorded only. GeneralTools has moved to it on a newer Kotlin; whether it exists on KGP 2.2.0 was not checked.
7. **vanniktech 0.37.0 exists** (released 2026-06-21, same minimums, tested up to Gradle 9.6.0 and KGP 2.4.0); not evaluated.
8. **`webtools-http` does not exist yet**, so the first-module sequencing (commit the dump with the first public declaration) is a statement of what BCV requires, not of anything observed in the repository.

**Considerations**

None. The ASM override is part of the recommended wiring; dropping it once the Java 11 floor has landed is a one-line removal, not a decision that blocks execution.
