# Research: the public shape of the policy and transport-settings configuration (`url-policy`)

[SpartanLaboratories/WebTools#64](https://github.com/SpartanLaboratories/WebTools/issues/64), unit 5 of the
HTTP client stack ([#55](https://github.com/SpartanLaboratories/WebTools/issues/55)). Question 4 of
[`README.md`](README.md). Written 2026-10-25 against the repository at `ad0ae63` plus the unit-5 branch.

## 1. Question

What public, binary-compatibility-checked shape should `OutboundUrlPolicy` (sealed `Trusted`/`Untrusted`),
`TransportSettings`, `CidrBlock` and `MixedAnswers` take in idiomatic Kotlin 2.2.0 common code, and what
convention do the later units' nested configuration builders follow?

An answer has to meet these requirements:

- No defaulted parameter on a public constructor or Stable Core function except a trailing builder lambda
  `= {}`.
- A new setting is addable in a feature release without a binary break for Kotlin callers.
- No public `data class`; `explicitApi()`; binary-compatibility-validator 0.18.2 dumps the JVM ABI.
- Common code, compiled for the JVM and checked for `js`.
- A developer's configuration mistake throws `IllegalArgumentException` when the value is built; text from
  outside the process returns a `Result`.
- Everything `toString()` prints may reach a log line, and the stack never logs internal network detail.

## 2. Bottom line

- **One derivation path: named values plus a `from` factory, no `forTrusted { }`/`forUntrusted { }`.**
  `TransportSettings.TrustedDefaults` and `TransportSettings.UntrustedDefaults` are companion values, and
  `TransportSettings(from) { }` is the only way to derive a modified copy. The same `from` overloads exist on
  the policy factories: `OutboundUrlPolicy.untrusted(from) { }` and `trusted(from) { }`. This is
  `kotlinx.serialization`'s `Json.Default` plus `Json(from) { }`, minus the one thing this repo forbids: its
  defaulted `from`. `from` is required, so the Stable Core signature has no `$default` bridge.
- **A policy builder has both `var settings: TransportSettings` and `fun settings(configure)`.** The block
  derives from the builder's current settings with `TransportSettings(settings, configure)`, so
  `untrusted { settings { callTimeout = 10.seconds } }` starts from the `Untrusted` defaults. This is the
  convention for later nested builders: an assignable property for a whole value, plus a same-named block
  function that starts from the property's current value.
- **Collections are read-only `Set`s, copied once at build, and builder `var`s of the read-only type.**
  `allowedPorts: Set<Int>?` (`null` is any port), `pinnedHosts`, `extraDeniedRanges` and
  `extraDeniedHostSuffixes` are `Set`s, because order carries no meaning and `Set` equality is
  order-free. Extend one with `+=` on the builder `var`. `HttpHeaders.Builder`'s add-functions fit its ordered,
  repeated entries and do not generalise to these.
- **Value equality, hand-written; `toString` prints counts, never the operational values.** Each value
  type overrides `equals`, `hashCode` and `toString`. A policy prints the number of pinned hosts, denied
  ranges and suffixes, and `CidrBlock` prints `CidrBlock(IPv4/8)` (family and prefix length), never the
  address.
- **Factories:** `TransportSettings(from) { }` is a top-level function in `TransportSettings.kt`, the shape
  of `HttpHeaders { }` and `HttpRequest(...) { }`. `OutboundUrlPolicy.trusted { }` and `untrusted { }` are
  companion functions, because the requested call syntax needs a receiver (precedent: `Url.parse`).
- **Sealed pair:** the sealed base cannot have an `internal` constructor (Kotlin allows only `protected` or
  `private`), so the base is constructor-less with abstract members; `Trusted` and `Untrusted` are nested
  final classes with `internal` constructors and nested `Builder`s.
- **Open design choice (Consideration 1): one public `@DslMarker` annotation for every builder in the
  module.** It scope-checks every nested builder lambda, at the cost of one public annotation class in the
  ABI and a source-level tightening of the builders already built. The recommendation is to adopt it now.

## 3. Findings

### F1. The Kotlin guidance: no defaults on published API, no `data class`, builder DSLs are the established alternative (established consensus; Kotlin docs, retrieved 2026-10-25)

The API guidelines for library authors, "Backward compatibility":

- Default arguments: adding them "can break compatibility", because "the signature of the method changed in
  the bytecode generated by the Kotlin/JVM compiler".
- `@JvmOverloads` "doesn't preserve binary compatibility for Kotlin callers".
- Data classes: "In API design, this strength becomes a weakness." Their generated constructor and `copy`
  change signature with every property.

[Source](https://kotlinlang.org/docs/api-guidelines-backward-compatibility.html). The guidelines do not
mention builders or DSLs, so the builder-lambda factory is common practice (F2 to F4), not a guideline. The
repo's prior research (`../../research/api-shape-and-failures.md` F7 and its Conventions table) already settles
Pattern A: a builder-lambda factory over an `internal` constructor. This document applies it and does not
re-argue it.

### F2. Named defaults plus a `from` factory is `kotlinx.serialization`'s shape; the defaulted `from` is the part to drop (common practice; kotlinx.serialization v1.12.0)

- `Json` is `public sealed class Json(...)` whose companion is `public companion object Default : Json(...)`.
  The factory is `public fun Json(from: Json = Json.Default, builderAction: JsonBuilder.() -> Unit): Json`
  over `public class JsonBuilder internal constructor(json: Json)`. The KDoc example is
  `Json(defaultJson) { prettyPrint = true }` with "Will inherit the properties of defaultJson".
- Its ABI dump (`kotlinx-serialization-json.api`, v1.12.0) therefore holds both
  `Json (Json, Function1)` and the synthetic `Json$default (Json, Function1, int, Object)`, the second being
  the signature that changes if the parameter list ever grows. Dropping the default for `from` removes that
  bridge and leaves the required form. This repo's own `HttpHeaders { }` is in the dump as
  `HttpHeaders(Function1)` plus `HttpHeaders$default(Function1, int, Object)`, which is the one default the
  conventions allow (a trailing `= {}`).
- `JsonConfiguration` has a hand-written `toString` and no `equals`; `Json` has neither (identity).
  [Json.kt](https://github.com/Kotlin/kotlinx.serialization/blob/v1.12.0/formats/json/commonMain/src/kotlinx/serialization/json/Json.kt),
  [JsonConfiguration.kt](https://github.com/Kotlin/kotlinx.serialization/blob/v1.12.0/formats/json/commonMain/src/kotlinx/serialization/json/JsonConfiguration.kt).
- Coil 3.6.3 has the same named-value idea: `ImageRequest.Defaults.DEFAULT` (`@JvmField val DEFAULT = Defaults()`).
  Its `copy(...)` takes a defaulted parameter per field, and `ImageRequest.newBuilder(context = this.context)`
  uses `@JvmOverloads`: both are the pattern this repo rejects for Stable Core.
  [ImageRequest.kt](https://github.com/coil-kt/coil/blob/3.6.3/coil-core/src/commonMain/kotlin/coil3/request/ImageRequest.kt).

### F3. Deriving a modified copy: `from` factory for values; `config { }`/`newBuilder()` for heavy objects (common practice)

- Ktor 3.6.0: `HttpClient.config(block: HttpClientConfig<*>.() -> Unit): HttpClient` "Returns a new
  [HttpClient] by copying this client's configuration and additionally configured by the [block] parameter".
  It copies a client that shares an engine, not a value. [HttpClient.kt](https://github.com/ktorio/ktor/blob/3.6.0/ktor-client/ktor-client-core/common/src/io/ktor/client/HttpClient.kt).
- OkHttp 5.5.0: `open fun newBuilder(): Builder = Builder(this)` on `OkHttpClient`, with the public
  `fun build(): OkHttpClient`. Apollo Kotlin v5.2.0 `ApolloClient.newBuilder()` and Coil's
  `ImageLoader.newBuilder()` are the same chained-builder form. All three need a public `build()`, so
  the builder cannot keep the repo's `internal fun build()`.
  [OkHttpClient.kt](https://github.com/square/okhttp/blob/parent-5.5.0/okhttp/src/commonJvmAndroid/kotlin/okhttp3/OkHttpClient.kt),
  [ApolloClient.kt](https://github.com/apollographql/apollo-kotlin/blob/v5.2.0/libraries/apollo-runtime/src/commonMain/kotlin/com/apollographql/apollo/ApolloClient.kt).
- Consequence here: a member `newBuilder()` would add a public `build()` and a public `Builder` constructor
  path to every configurable type. `X(from) { }` adds one top-level function per type and keeps
  `Builder.build()` `internal`. The facade's need ("raise `maxConcurrentRequests` to the budget's burst")
  reads `TransportSettings(policy.settings) { maxConcurrentRequests = maxOf(maxConcurrentRequests, burst) }`:
  the lambda reads the seeded value before it assigns.

### F4. `@DslMarker`: what it does, who declares it publicly, what is unknown about `internal` (established consensus for semantics; common practice for visibility)

- Semantics (stdlib KDoc, "Since Kotlin 1.1"): "two implicit receivers of the same DSL are not accessible in
  the same scope" and "the closest one wins". A receiver is marked if its type, its type's classifier or any
  superclass or superinterface is marked. The type-safe-builders page: "Only the nearest receiver's members
  and extensions are accessible within a lambda", and an outer receiver stays reachable only through
  `this@label`. The marker does not hide top-level functions, and it checks implicit receivers only.
  [DslMarker](https://kotlinlang.org/api/core/kotlin-stdlib/kotlin/-dsl-marker/index.html),
  [Type-safe builders](https://kotlinlang.org/docs/type-safe-builders.html).
- Each receiver class must carry it; there is no inheritance from the lambda's function type unless the
  marker is on the type usage. A builder with no shared superclass is annotated one by one.
- Public in every library found: Ktor 3.6.0 `@DslMarker @Target(CLASS, TYPEALIAS, TYPE, FUNCTION) public
  annotation class KtorDsl` in `io.ktor.utils.io`, applied as `@KtorDsl public class HttpClientConfig<T>`;
  kotlinx.html 0.12.0 `@DslMarker annotation class HtmlTagMarker`. `Json`'s `JsonBuilder`, OkHttp, Coil and
  Apollo's client builders carry none (their builders are flat or chained).
- **Not established:** whether an `internal` marker applied to a public builder still gives consumers the
  scope check, and whether the BCV dump records the marker on the builder. No source says; the verification
  needs a compile, which this research did not run (Gap 1). An `internal` marker would save one public
  annotation class at the risk of silently not protecting consumers, so the recommendation uses a public one.

### F5. Sealed classes: constructors, subclass location and the shape of the dump (established consensus; Kotlin docs, retrieved 2026-10-25, plus repo and library dumps)

- "Constructors of sealed classes can have one of two visibilities: `protected` (by default) or `private`";
  the page's example comment says "public and internal constructors are not allowed in sealed classes". So
  `sealed class OutboundUrlPolicy internal constructor()` does not compile. Direct subclasses must be in
  the same package and module. [Sealed classes](https://kotlinlang.org/docs/sealed-classes.html).
- The JVM shape is an `abstract class` with a synthetic public constructor ending in `DefaultConstructorMarker`.
  Both `Json` (`public synthetic fun <init> (JsonConfiguration, SerializersModule, DefaultConstructorMarker)`) and
  this repo's `HttpFailure` (`webtools-http.api`) show it. Consumers outside the module cannot use that
  constructor. If the base constructor takes parameters, those types are in the dump, so keep the base
  parameterless and let the subclasses supply state through abstract members.
- Adding an abstract member to a `sealed` base is not a break for consumers, because they cannot subclass it.
  Adding a third subclass breaks their exhaustive `when`; the pair is the contract.
- `sealed` plus a companion that creates the subclasses is how `Json` works (`JsonImpl` is a private
  subclass), and the repo already ships a companion factory: `Url.parse`, in the dump as `Url$Companion.parse-IoAF18A`.

### F6. Collections: copy once, expose read-only, `var` of the read-only type in the builder (common practice)

- Kotlin's coding conventions: "Always use immutable collection interfaces (`Collection`, `List`, `Set`,
  `Map`) to declare collections which are not mutated."
  [Coding conventions](https://kotlinlang.org/docs/coding-conventions.html).
- OkHttp 5.5.0 `Builder.protocols(protocols: List<Protocol>)` makes a private copy first ("// Create a private
  copy of the list."), validates, and `OkHttpClient` stores `toImmutableList()` snapshots. The JVM-only
  unmodifiable wrapper is unavailable in common code, so the repo's own precedent is the model:
  `HttpResponse` stores `redirectChain.toList()` and exposes the stored list; `HttpHeaders` copies on
  construction. Neither prevents a cast to `MutableList`; both rely on the declared type.
- `Set.plus` on a `var Set<T>` makes `pinnedHosts += "a.example"` compile as `pinnedHosts = pinnedHosts + "a.example"`
  with no extra ABI. (Kotlin language behaviour of `+=` on a `var` of a read-only collection; not separately sourced.)

### F7. Equality and `toString` of config values (common practice, mixed)

- Identity is what `Json`, `JsonConfiguration`, `HttpClientConfig` and `OkHttpClient` have; they own
  resources or are mutable. Pure-data configuration with a stable binary shape either hand-writes the three
  methods (this repo: `HttpHeaders`, `Url`, `RefusalReason`; `JsonConfiguration` writes `toString` only) or generates them
  with the Poko compiler plugin (Coil: `@Poko class Defaults`). Poko "automatically generates `toString`,
  `equals`, and `hashCode` functions" and "no `copy` or `componentN` functions". The repo's rule is hand-written;
  adding a compiler plugin to a Stable Core module for three classes is not warranted.
- This repo's `toString` precedent prints names and counts, never values: `HttpHeaders` ("prints the names in
  order ... and never a value") and `HttpRequest` (header names and the body's size). A configuration with
  operational detail (denied internal ranges, host suffixes, pinned hosts) follows: print the number.

### F8. Naming: factory and constant names (common practice; repo precedent decides)

- Kotlin's conventions say a factory function "can have the same name as the abstract return type" and "avoid
  giving it the same name as the class itself ... Only if there is really no special semantics, you can use
  the same name as the class". `Json { }`, `HttpClient(engine) { }`, and this repo's `HttpHeaders { }` and
  `HttpRequest(...) { }` all use the class name, and `TransportSettings(from) { }` has no special semantics.
- The conventions name deeply immutable object `val`s in SCREAMING_SNAKE_CASE, yet this repo names companion
  constants in PascalCase (`RefusalReason.Scheme`, `WallClock.System`; `Json.Default` also). The recommendation
  follows the repo within the module.
- Other libraries' setting names for the same concepts: OkHttp `callTimeout`, `connectTimeout`, `readTimeout`,
  `writeTimeout`, `followRedirects`, `followSslRedirects`, `Dispatcher.maxRequests`/`maxRequestsPerHost`,
  `ConnectionPool` keep-alive duration; Ktor `HttpTimeout` `*TimeoutMillis`, `HttpRedirect.allowHttpsDowngrade`.
  The `Duration` overloads that OkHttp 5.5.0 adds confirm `kotlin.time.Duration` as the public type.

## 5. Pitfalls and regrets

1. **A defaulted `from` is a `$default` bridge in the dump** (`Json$default`). Required `from` and the
   `= {}` lambda are the only defaults.
2. **Hand-written equality drifts.** Adding a setting without touching `equals`/`hashCode`/`toString`
   compiles and passes everything except an equality test. Cover it with one Level 2 test per builder
   property: change only that property from the defaults and assert the result is not equal and prints differently.
3. **Default numbers are a contract.** `TransportSettings.UntrustedDefaults` holds today's numbers (15 s,
   5 s, 5 s, 5 s, 2 MiB, 3, false, 8, 2, 4 s). A derived value tracks them, so changing a default number later
   changes behaviour for every consumer who did not set it. Document the numbers in the KDoc and treat a change
   as a behaviour change.
4. **Sealed-base static-initialiser cycle (derived, not sourced).** A static field in the sealed base's
   companion that holds a `Trusted`/`Untrusted` instance makes base initialisation construct a subclass, and a
   second thread initialising a subclass first can deadlock on the two class-initialisation locks (JLS 12.4.2).
   Keep the default values in `TransportSettings`'s companion, which is not a base of anything, and construct
   policies only inside the factory functions.
5. **`null` meaning "any port" next to an empty set.** `allowedPorts = emptySet()` would refuse everything; the
   builder rejects it with `IllegalArgumentException` and the KDoc says to use `null`.
6. **Builder aliasing.** `pinnedHosts = mySet` holds the caller's reference until the build copies it. The
   builders are not thread-safe and the KDoc says to use them inside the lambda only (the `HttpHeaders.Builder`
   wording).
7. **Property and same-named function in one builder** (`settings` and `settings { }`) is legal Kotlin and has no
   JVM clash (`getSettings`, `setSettings`, `settings(Function1)`). With a `@DslMarker` the inner block cannot
   reach the outer builder's `settings` implicitly, which is intended.
8. **The internal primary constructor must not share a signature with the top-level factory.** Both are called
   `TransportSettings(...)` in-module; give the constructor the full value list and the factory `(from, configure)`.
9. **Duration-typed accessors are mangled** (`getCallTimeout-<hash>`), so a property's type can never change
   from `Duration` without a break. Property renames are breaks too; choose the names once.
10. **A `when` over an enum in consumer code** (`MixedAnswers`) fails to compile or throws `NoWhenBranchMatchedException`
    if an entry is added. The enum is a consumer-chosen input, so the library never branches on a foreign
    value, but a consumer that reads `policy.mixedAnswers` in a `when` should keep an `else`; the KDoc says so.

## 6. Recommendation for this repo

Pattern A everywhere, with a required `from` for derivation, a settings block that seeds from the current
value, and counts instead of values in `toString`. The Kotlin below is the public surface the unit adds; bodies
are elided, the dump shape follows from it.

```kotlin
package com.spartanlabs.webtools.http

/** Marks every configuration builder of the module so that a nested lambda cannot reach its outer builder implicitly. */
@DslMarker
@Target(AnnotationTarget.CLASS)
public annotation class WebToolsDsl                       // Consideration 1

// ---- TransportSettings.kt -------------------------------------------------------------------------
public class TransportSettings internal constructor(
    callTimeout: Duration, connectTimeout: Duration, readTimeout: Duration, writeTimeout: Duration,
    maxResponseBodyBytes: Long, maxRedirects: Int, allowHttpsToHttp: Boolean,
    maxConcurrentRequests: Int, maxConcurrentRequestsPerHost: Int, idleConnectionLifetime: Duration,
) {
    public val callTimeout: Duration                      // all hops together
    public val connectTimeout: Duration
    public val readTimeout: Duration
    public val writeTimeout: Duration
    public val maxResponseBodyBytes: Long                 // decoded bytes
    public val maxRedirects: Int
    public val allowHttpsToHttp: Boolean
    public val maxConcurrentRequests: Int
    public val maxConcurrentRequestsPerHost: Int
    public val idleConnectionLifetime: Duration

    override fun equals(other: Any?): Boolean             // every field
    override fun hashCode(): Int
    override fun toString(): String                       // "TransportSettings(callTimeout=15s, ...)": numbers only

    @WebToolsDsl
    public class Builder internal constructor(from: TransportSettings) {
        public var callTimeout: Duration                  // one var per setting, seeded from `from`
        public var connectTimeout: Duration
        public var readTimeout: Duration
        public var writeTimeout: Duration
        public var maxResponseBodyBytes: Long
        public var maxRedirects: Int
        public var allowHttpsToHttp: Boolean
        public var maxConcurrentRequests: Int
        public var maxConcurrentRequestsPerHost: Int
        public var idleConnectionLifetime: Duration
        internal fun build(): TransportSettings           // validates; IllegalArgumentException
    }

    public companion object {
        public val TrustedDefaults: TransportSettings     // 30 s, 10 s, 10 s, 10 s, 5 MiB, 5, false, 16, 5, 4 s
        public val UntrustedDefaults: TransportSettings   // 15 s, 5 s, 5 s, 5 s, 2 MiB, 3, false, 8, 2, 4 s
    }
}

/** Derives a settings value: starts from [from], applies [configure], validates. */
public fun TransportSettings(from: TransportSettings, configure: TransportSettings.Builder.() -> Unit): TransportSettings

// ---- OutboundUrlPolicy.kt -------------------------------------------------------------------------
public sealed class OutboundUrlPolicy {                   // protected, parameterless constructor (the default)
    public abstract val settings: TransportSettings

    public class Trusted internal constructor(pinnedHosts: Set<String>, allowCleartext: Boolean, settings: TransportSettings)
        : OutboundUrlPolicy() {
        public val pinnedHosts: Set<String>               // empty: any host
        public val allowCleartext: Boolean
        override val settings: TransportSettings
        override fun equals(other: Any?): Boolean
        override fun hashCode(): Int
        override fun toString(): String                   // "Trusted(pinnedHosts=2, allowCleartext=false, settings=TransportSettings(...))"

        @WebToolsDsl
        public class Builder internal constructor(from: Trusted) {
            public var pinnedHosts: Set<String>
            public var allowCleartext: Boolean
            public var settings: TransportSettings        // whole value
            public fun settings(configure: TransportSettings.Builder.() -> Unit)   // = TransportSettings(settings, configure)
            internal fun build(): Trusted                 // validates; IllegalArgumentException
        }
    }

    public class Untrusted internal constructor(
        allowedPorts: Set<Int>?, extraDeniedRanges: Set<CidrBlock>, extraDeniedHostSuffixes: Set<String>,
        mixedAnswers: MixedAnswers, settings: TransportSettings,
    ) : OutboundUrlPolicy() {
        public val allowedPorts: Set<Int>?                // null: any port; default {80, 443, 8080, 8443}
        public val extraDeniedRanges: Set<CidrBlock>
        public val extraDeniedHostSuffixes: Set<String>
        public val mixedAnswers: MixedAnswers             // default Reject
        override val settings: TransportSettings
        override fun equals(other: Any?): Boolean
        override fun hashCode(): Int
        override fun toString(): String                   // ports listed; ranges and suffixes as counts

        @WebToolsDsl
        public class Builder internal constructor(from: Untrusted) {
            public var allowedPorts: Set<Int>?
            public var extraDeniedRanges: Set<CidrBlock>
            public var extraDeniedHostSuffixes: Set<String>
            public var mixedAnswers: MixedAnswers
            public var settings: TransportSettings
            public fun settings(configure: TransportSettings.Builder.() -> Unit)
            internal fun build(): Untrusted
        }
    }

    public companion object {
        public fun trusted(configure: Trusted.Builder.() -> Unit = {}): Trusted
        public fun trusted(from: Trusted, configure: Trusted.Builder.() -> Unit): Trusted
        public fun untrusted(configure: Untrusted.Builder.() -> Unit = {}): Untrusted
        public fun untrusted(from: Untrusted, configure: Untrusted.Builder.() -> Unit): Untrusted
    }
}

// ---- CidrBlock.kt, MixedAnswers.kt ----------------------------------------------------------------
public class CidrBlock private constructor(/* family, address bytes, prefix length */) {
    override fun equals(other: Any?): Boolean             // family, masked address, prefix
    override fun hashCode(): Int
    override fun toString(): String                       // "CidrBlock(IPv4/8)": family and prefix only
    public companion object {
        public fun parse(text: String): Result<CidrBlock> // constant failure messages; never echoes `text`
    }
}

public enum class MixedAnswers { Reject, DropDenied }
```

Reasoning behind the choices:

1. **Named values plus `from`, not companion factories.** `TransportSettings.forUntrusted { }` would be a second
   way to do what `TransportSettings(UntrustedDefaults) { }` does, doubles the Stable Core functions per default set, and
   cannot express "start from a value I already have". Named values also give the KDoc a place to state the numbers.
   `TrustedDefaults`/`UntrustedDefaults` reads as a settings set, and `OutboundUrlPolicy.Trusted` as a policy; the
   suffix removes the confusion a bare `TransportSettings.Trusted` would invite.
2. **`from` overloads on the policy factories, with no policy `withSettings`.** One mechanism covers a settings
   change (`untrusted(p) { settings { ... } }`) and any other change. The facade that raises concurrency uses an
   `internal` helper that does `when (policy) { is Trusted -> trusted(policy) { settings = s } ... }`, which costs no ABI and uses the
   closed pair the way a consumer would. The `from` overloads are additive: a smaller first release can defer them
   and add them later without a break.
3. **Settings property and block both.** The property takes a shared `TransportSettings` value across policies;
   the block is the common case and the shape the later `headers { }` and `budget(windows) { }` blocks follow.
   The block runs against the property's current value, so `settings = X` followed by `settings { }` modifies `X`; the
   KDoc states that order matters.
4. **Collections as `var Set`.** One accessor pair per collection; the policy stays seedable from `from` and
   replaceable; extension is `+=`. Validation (each port 1 to 65535, non-empty `allowedPorts` when non-null, a
   suffix or host that is not a bare lowercase-able name) runs in `build()` so one message names the property.
   `Set` rather than `List` because order has no meaning, equality is order-free, and a duplicate is not an error.
5. **Settings validation at build** (suggested checks, not researched against sources): each timeout positive and
   finite, `maxResponseBodyBytes >= 1`, `maxRedirects >= 0`, `maxConcurrentRequests >= 1`,
   `1 <= maxConcurrentRequestsPerHost <= maxConcurrentRequests`.
6. **Marker.** One annotation, `@WebToolsDsl`, on every `Builder`, existing `HttpHeaders.Builder` and
   `HttpRequest.Builder` included, so `headers { }` inside the later client configuration is scope-checked. See
   Consideration 1.
7. **Sealed base.** Parameterless and abstract-only, so its dump entry is the stable `<init>(DefaultConstructorMarker)`.
   `Trusted` and `Untrusted` are `final` (no `open`): the closed pair is the contract, and a consumer who wants a
   different policy configures one of the two. Returning the precise `Trusted`/`Untrusted` from the factories lets a
   caller read `.allowedPorts` without a cast.

Rejected: `forTrusted`/`forUntrusted` as the only path (above); `newBuilder()` (needs a public `build()`);
`data class` (F1); a `Poko` plugin (F7); `List` for the collections; add-functions for the sets (they cannot
express replacement and need a matching `remove`); a `withSettings` member on the sealed base (a second derive path);
`internal` constructor on the sealed base (does not compile, F5).

## 7. Considerations

### Consideration 1: one public `@DslMarker` annotation for the module's builders

- **Options.**
  - **(a) Adopt `@WebToolsDsl` now**, on `TransportSettings.Builder`, both policy builders, and the already-built
    `HttpHeaders.Builder` and `HttpRequest.Builder`; later units annotate theirs. Cost: one public annotation class in the
    ABI forever, and a source-level tightening of the two built builders (a lambda that today calls an outer
    builder's member implicitly stops compiling; `this@label` fixes it). I expect the dump to be unchanged for the builders
    (BCV is not known to record annotation use; the new annotation class itself appears; Gap 1).
  - **(b) No marker.** No ABI cost. An implicit call to an outer builder from a nested block compiles, and the
    nested configurations of the later client (`headers { }`, `budget(windows) { }`) are exposed to it. Adding the marker
    afterwards is a source break for any consumer relying on that call, so the choice is cheapest now.
  - **(c) An `internal` marker.** Saves the public class; whether it protects consumers is not established (Gap 1).
- **Recommendation: (a).** Ktor and kotlinx.html both ship a public marker, and the nested builders this stack
  plans (policy → settings; client → headers, budget) are the case the Kotlin documentation motivates.

## 9. Gaps

1. **No compile was run, so three compile-level facts are unverified:**
   - whether an `internal` `@DslMarker` annotation on a public builder still scopes consumers' lambdas;
   - whether BCV 0.18.2 records the marker on the builder classes (I expect only the annotation class itself);
   - the exact dump lines for the companion functions with a trailing default lambda. I infer `OutboundUrlPolicy$Companion.trusted(Function1)`
     plus a synthetic `trusted$default(Companion, Function1, int, Object)` from the `Url$Companion.parse` and `HttpHeadersKt.HttpHeaders$default` entries already in `webtools-http.api`.
   The first `apiDump` of the implementation is the check, compared against section 6.
2. **The static-initialisation deadlock in pitfall 4 is derived from JLS class-initialisation rules, not from a source I opened.** The advice (no subclass instance in the sealed base's static state) costs nothing, so it stands.
3. **Whether Kotlin 2.2.0 emits `PermittedSubclasses` at `jvmTarget = 11`** (it matters only for Java callers, a non-goal) is not confirmed; the only material found was a Slack thread and a KEEP discussion.
4. **`CidrBlock` details are outside this question:** whether `parse("10.0.0.5/8")` rejects set host bits or masks them (I would reject, matching the strict-parse stance, but that belongs to the classifier research), whether IPv4-mapped IPv6 blocks are accepted, and whether a public `contains(address)` is wanted (leave it out of 1.0: additive later).
5. **Host and suffix normalisation and validation rules** (`pinnedHosts`, `extraDeniedHostSuffixes`: case, trailing dot, IDNA, leading dot) belong to the host-rules question; this document fixes only that they are validated in `build()` and stored normalised.
6. **The settings validation list in section 6 point 5 is my suggestion**, not checked against an upstream's behaviour (OkHttp accepts 0 as "no timeout"; the design has no unbounded value).
7. **Poko's reason for existing** (binary compatibility) is not stated in its README; only what it generates is cited.
8. **Library versions:** "latest" for Coil, Apollo, kotlinx.serialization, kotlinx.html and Ktor was read from the GitHub releases API on 2026-10-25; OkHttp is pinned to the repo's 5.5.0 (5.5.1 exists).
