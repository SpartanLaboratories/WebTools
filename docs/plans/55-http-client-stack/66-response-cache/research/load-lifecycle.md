# How a shared load starts, ends and reports (`CaffeineResponseCache`, kotlinx-coroutines 1.10.2)

## Question

How should the coroutine behind a shared cache load start, end and report its outcome under kotlinx-coroutines 1.10.2, in production and under `runTest`, so that every waiter receives exactly one outcome?

An answer has to meet these requirements, which are facts of the design:

- A `CancellationException` never reaches a waiter that is still active; a waiter's own cancellation is thrown as `CancellationException`.
- Every waiter returns exactly one outcome and never hangs, including when `close()` runs between Caffeine's mapping function and the start of the load.
- A fatal `Error` reaches every waiter and is not reported a second time elsewhere.
- A loader's `Exception` becomes the call's failure; `close()` is non-suspending, idempotent and never throws; every waiter and every later call gets `Result.failure(HttpFailure.Closed("cache"))`.
- The load never runs in a caller's context; one waiter's cancellation leaves the load and the other waiters intact.
- Level 2 tests are deterministic on the published `VirtualClock`.

Evidence labels: **documented** (library source, KDoc or tests at the pinned tag `1.10.2`, commit `5f8900478a8e20c073145b1608fbc71fe3d7378b`); **common practice** (what mature libraries visibly do); **inference** (my reading of documented behaviour, not a quoted statement). Nothing was built or run; behaviour that only a run would show is in *Gaps* with the unit test that would establish it.

## Bottom line

- **Start with `launch` (`CoroutineStart.DEFAULT`) in the `SupervisorJob` scope, not `async`; the body catches everything except the cancellation `close()` causes and completes the shared future normally with a value.** The value is one of four outcomes: loaded, failed (an `Exception`), fatal (an `Error`, kept by identity), closed. The body never throws, so `launch`'s `handleJobException` path (thread uncaught-exception handler in production, the test module's exception collector under `runTest`) is never used and a fatal `Error` is reported once, to its waiters. `async` under a supervisor holds a failure silently in a `Deferred` nobody awaits, and buys nothing because the future is already the result channel.
- **The stack-level cache research's recommended shape (`launch { f.complete(load()) }` plus an `invokeOnCompletion` that maps any cancellation to `Closed` and anything else to `completeExceptionally`) has three defects, all from the source.** (1) A cancellation thrown by the loader itself (a `withTimeout` expiring) ends the load coroutine with a `CancellationException` while the cache is open, and the handler would tell every waiter `Closed`. (2) A fatal `Error` is reported to the uncaught-exception handler by `launch`, then the handler completes the future exceptionally, which Caffeine logs at `WARNING` and which kotlinx-coroutines may re-create under `-ea`: two reports and a changed identity. (3) Release of the waiters waits for the job's completion, which waits for the loader to unwind; a loader that ignores cancellation, or a `launch` that throws on a rejecting dispatcher, leaves joined waiters hanging.
- **Tell `close()` from the loader's own cancellation inside the body with `currentCoroutineContext().ensureActive()` after catching `CancellationException`** (the idiom the `Deferred.await` KDoc prescribes). If the load coroutine is still active the cancellation came from inside the loader and becomes a failure value that is not a `CancellationException`; if not, `close()` caused it and the body rethrows. Never put a `CancellationException` into a `Result.failure`: `getOrThrow()` would throw it into an active caller, where a parent `launch` treats it as normal cancellation.
- **Guarantee "never hangs" with the public API only: `close()` sets a flag, cancels the scope, then completes every future in `asMap().values` with the closed outcome; the starter re-checks the flag after `cache.get` returns and completes its own future if closed; `job.invokeOnCompletion` stays as a last safety net.** `Job.invokeOnCompletion(onCancelling = true, ...)`, the variant that fires at the moment of cancellation, is `@InternalCoroutinesApi` and documented "Shouldn't be used by anyone". `CompletableFuture.complete` is first-wins, so every extra completer is harmless.
- **A waiter awaits with `f.asDeferred().await()` and wraps it in `catch (e: CancellationException) { currentCoroutineContext().ensureActive(); closed }`.** Because the future only ever completes with a value, the only `CancellationException` a waiter can see is its own; the guard keeps the requirement true even if something cancels the shared future. The cost of a cancelled waiter is one `CompletableDeferred` and one callback on the shared future until the future completes.
- **`runTest` 1.10.2 drains the whole shared scheduler at the end of the body (`testScheduler.advanceUntilIdleOr { false }`), including the cache's own queued coroutines and pending `delay`s, before it collects unhandled exceptions; its default `timeout` is 60 s of real time.** A cache scope that is not a child of the test is neither waited for nor reported as a leaked child, but an exception that escapes a coroutine in it fails the test, through the global exception collector. The Level 2 cases below drive each interleaving with `advanceBy` plus assertions on `isCompleted`; only the close-before-start case needs a parking `loadDispatcher`.

## Findings

### F1. `launch` and `async` in a supervisor scope: where a thrown `Error` goes (documented)

- `launch` builds a `StandaloneCoroutine` whose `handleJobException` is `handleCoroutineException(context, exception)` (`Builders.common.kt`, 1.10.2). `async` builds a `DeferredCoroutine`, which does not override `handleJobException`; `JobSupport` documents the default as `false` and says it "is designed to be overridden by launch-like coroutines (`StandaloneCoroutine` and `ActorCoroutine`) that don't have a result type that can represent exceptions" (`JobSupport.kt`).
- For a root coroutine under a `SupervisorJob`, `finalizeFinishingState` runs `cancelParent(finalException) || handleJobException(finalException)`. `SupervisorJobImpl.childCancelled` returns `false` (`Supervisor.kt`), and `cancelParent` returns `isCancellation` (true only for a `CancellationException`) when there is no handling parent. So an `Error` from a `launch` body reaches `handleCoroutineException`; an `Error` from an `async` body is stored in the `Deferred` and reported nowhere unless someone calls `await` (the exception-handling guide: "[async] builder always catches all exceptions and represents them in the resulting [Deferred] object").
- `handleCoroutineException` uses a `CoroutineExceptionHandler` from the context if present; with none, `handleUncaughtCoroutineException` first offers the exception to every service-loaded handler (`ServiceLoader.load(CoroutineExceptionHandler::class.java, ...)`, `jvm/src/internal/CoroutineExceptionHandlerImpl.kt`) and then calls `currentThread.uncaughtExceptionHandler.uncaughtException(currentThread, exception)`. On a plain JVM with `kotlinx-coroutines-core` alone the service list is empty (only `kotlinx-coroutines-android` and `kotlinx-coroutines-test` ship one), so the thread's handler prints the stack trace and the worker thread survives.
- A `launch` body that never throws (it catches `Throwable` other than the cancellation `close()` causes) never reaches any of this. That is what makes "reported once" hold, and what keeps a Level 2 test that provokes an `Error` from failing through the collector (F5).

### F2. A job created in a cancelled scope (documented, plus the library's own tests)

- `launch` calls `coroutine.start(start, ...)`; `DEFAULT` is `startCoroutineCancellable`, which dispatches through `resumeCancellableWith`. When the dispatched task runs, `DispatchedTask.run` checks `job.isActive` and, if the job was cancelled, resumes the continuation with the cancellation instead of entering the body (`DispatchedTask.kt`). `AtomicCancellationCommonTest.testCancellableLaunch` states it: `expectUnreached() // will get cancelled before start`.
- `ATOMIC` "is guaranteed to start executing even if it was cancelled" (`@DelicateCoroutinesApi`); `UNDISPATCHED` runs "until its first suspension point in the current thread" and "Even if the coroutine was cancelled already, its code will still start running" (`CoroutineStart.kt`; `testAtomicLaunch`, `testUndispatchedLaunch`). `UNDISPATCHED` would run the first segment of the load in the caller's thread, which the design forbids; `ATOMIC` would run a loader after `close()`. Both are rejected; `DEFAULT` is the one that skips the body of a load started after `close()`.
- A child attached to a parent that is cancelling or already completed is cancelled at once: `attachChild` documents that "such a child will receive an immediate notification on cancellation", and for a completed parent it invokes the node with the parent's completion cause. With a dispatching `loadDispatcher` the child's state is "cancelling" from the moment `launch` returns, but it completes only when the dispatcher runs the queued task.
- `Job.invokeOnCompletion(handler)`: "When the job is already complete, then the handler is immediately invoked with the job's exception or cancellation cause or `null`", and "There is no guarantee on the execution context in which the [handler] is invoked" (`Job.kt`). For a job cancelled before it started, the handler registered after `launch` returns is queued on the job and runs when the dispatcher runs the dead task, on that dispatcher's thread, with a `CancellationException` (the scope's `JobCancellationException`) as cause. If the job has completed by the time of registration (a fast loader on a pool thread), it runs inline on the registering thread with `null` (normal completion). `CancelledParentAttachTest` registers a handler after `launch` into a cancelled parent for every `CoroutineStart` entry and expects it to run.
- The variant that would fire at cancellation instead of completion, `invokeOnCompletion(onCancelling = true, invokeImmediately = true, handler)`, is annotated `@InternalCoroutinesApi` and documented "Kept for preserving compatibility. Shouldn't be used by anyone."

### F3. A cancellation the loader throws on its own (documented; inference for the classification rule)

- `withTimeout` runs its block in a `TimeoutCoroutine`, a scoped coroutine. `JobSupport.isScopedCoroutine` documents that scoped coroutines "always handle any exception happened within -- they just rethrow it to the enclosing scope. Examples of scoped coroutines are `coroutineScope`, `withTimeout` and `runBlocking`", and `cancelParent` returns early for them. So when a loader's `withTimeout` expires, `TimeoutCancellationException` (a `CancellationException`) is thrown to the loader's caller and **the load coroutine itself is not cancelled**: its `isActive` is still true.
- `catchNonFatal` rethrows `CancellationException`, so such an exception leaves the loader call and, with the shape `launch { f.complete(load()) }`, leaves the body. The coroutine then completes as cancelled with that exception as its cause (`cancelParent`: "CancellationException is considered "normal" and parent usually is not cancelled when child produces it"), the supervisor and the scope are unaffected, and `invokeOnCompletion` receives the `TimeoutCancellationException`. By cause alone it cannot be told from the `JobCancellationException` that `close()` produces: both are `CancellationException`.
- The distinguishing fact is the load coroutine's own state. `close()` cancels the scope's job, which cancels the load's job before any cancellation exception is observed in the body, so after catching a `CancellationException` in the body `currentCoroutineContext().isActive` is false exactly when `close()` (or an enclosing cancellation) caused it. The `Deferred.await` KDoc prescribes this idiom for the same ambiguity: `catch (e: CancellationException) { currentCoroutineContext().ensureActive() // throws if the current coroutine was cancelled; processException(e) }`. A flag of the cache's own would also work but adds a second source of truth; the job state is the one the library itself uses. A race that classifies a loader's cancellation as `close()` can only happen after `close()` started, so the waiters' `Closed` is correct anyway.
- What the waiter should receive: a failure value that is not a `CancellationException`, with the original kept as its `cause` (a `CancellationException` as a *cause* is harmless; only the thrown type matters). The coroutines guide says "inside a cancelled coroutine `CancellationException` is considered to be a normal reason for coroutine completion" and that `TimeoutCancellationException` "is a subclass of [CancellationException]". If a `Result.failure(ce)` reached a caller and was unwrapped with `getOrThrow()`, the `ce` would be thrown into a coroutine whose job is active; a parent `launch` ends such a coroutine silently as if cancelled. The same rule applies to a `Result.failure(CancellationException)` the loader returns as a value: treat it like a thrown one.

### F4. Waiting: `asDeferred()` in 1.10.2 (documented)

- `CompletionStage.asDeferred()` (`jvm/src/future/Future.kt`): if the future `isDone`, it returns `CompletableDeferred(future.get() as T)`, or, when `get()` throws, a deferred completed exceptionally with `(e as? ExecutionException)?.cause ?: e`. Otherwise it creates a `CompletableDeferred`, registers `handle { value, exception -> ... }` on the future (an exception is unwrapped with `(exception as? CompletionException)?.cause ?: exception`), and `result.invokeOnCompletion(handler = CancelFutureOnCompletion(future))`.
- `CancelFutureOnCompletion.invoke` does `if (cause != null && !future.isDone) future.cancel(false)`: the shared future is cancelled only if the per-call `CompletableDeferred` completes with a cause while the future is still open. Awaiting a deferred never cancels it, and that deferred is completed only by the future's own `handle` callback, so the cancel is unreachable in the intended use. This is the mechanism behind "one waiter's cancellation leaves the load intact"; `CompletionStage.await()` instead does `future.cancel(false)` in `invokeOnCancellation`.
- When a waiter is cancelled while the load runs, its `await` disposes its own handler on the `CompletableDeferred`, but the `handle` callback stays on the shared future's completion stack until the future completes, then is released. The residue per cancelled call is that callback plus one `CompletableDeferred`. It is bounded by the number of calls that joined during one load; it is unbounded only if the future never completes, which is why the completion guarantee in F6 matters (inference from the structure above; see Gaps).
- A `Deferred.await()` throws `CancellationException` "in two cases: if the coroutine in which [await] was called got cancelled, or if the [Deferred] itself got completed with a [CancellationException]". With a future that only completes with a value, only the first case occurs. There is a "prompt cancellation guarantee": a waiter cancelled while suspended throws even if the result is ready, so a waiter cancelled in the same instant the load finishes gets its own `CancellationException`, and the loaded entry still lands in the cache. A hit does not suspend, so a call made from an already-cancelled coroutine that finds a completed future returns the value without a check; add `currentCoroutineContext().ensureActive()` at the top of `getOrLoad` if "a cancelled caller never receives a value" is wanted.
- Exceptional completion is a poor carrier for a fatal `Error` (stack-trace recovery): `RECOVER_STACK_TRACES = DEBUG && systemProp(...)`, and `DEBUG` is on when assertions are enabled (`jvm/src/Debug.kt`), which Gradle test runs have by default. Recovery may re-create the exception through a reflective constructor with the original as cause, which is also what `CallBridge.kt` in this module guards against by resuming values, never throwables. Carrying the `Error` as a value (F5) preserves identity: `throw outcome.error` rethrows the original instance.

### F5. A fatal `Error` and the exception collector under `runTest` (documented)

- `kotlinx-coroutines-test` 1.10.2 registers `ExceptionCollectorAsService` through `META-INF/services/kotlinx.coroutines.CoroutineExceptionHandler`. Its KDoc: "If [addOnExceptionCallback] is called, the provided callback will be evaluated each time [handleCoroutineException] is executed and can't find a [CoroutineExceptionHandler] to process the exception." `TestScopeImpl.enter()` registers `ExceptionCollector.addOnExceptionCallback(lock, this::reportException)` (unless `catchNonTestRelatedExceptions` is turned off), so an exception that reaches `handleUncaughtCoroutineException` from **any** coroutine in the JVM, test child or not, is stored by the active `runTest` and thrown from `runTest` after the body ("Unhandled exceptions will be thrown at the end of the test"). The collector then throws `ExceptionSuccessfullyProcessed`, so the thread's handler is skipped.
- When no `runTest` is active but one ran earlier in the JVM, the collector is enabled: it stores the exception in `unprocessedExceptions`, returns false (so the thread handler also fires), and the **next** `runTest` fails with `UncaughtExceptionsBeforeTest`. A cache load that outlives its test and throws can therefore fail an unrelated later test. Fan-out is to every active callback ("it's less big of a deal to observe multiple concurrent reports ... than not to observe the report in the exact callback").
- Consequence for the design: if the body let an `Error` escape (the parent shape), a Level 2 test that provokes an `Error` would fail at the end of `runTest` no matter how the waiters handled it, because the cache's scope has no `CoroutineExceptionHandler` and none can be injected into `TestScope`. A body that delivers the `Error` as a value makes the case testable with `assertFailsWith`/`assertSame` on the waiters.

### F6. Completion paths of the shared future, and what can leave it open (documented, inference)

- `scope.launch` can throw. `startCoroutineCancellable` runs inside `runSafely`; if the dispatcher's `dispatch` throws, `dispatcherFailure` calls `completion.resumeWith(Result.failure(reportException))` and then `throw reportException` ("This method is invoked when we failed to start a coroutine due to the throwing dispatcher implementation"). A rejecting executor-backed `loadDispatcher` makes `launch` throw after the future is already in the cache; waiters that joined it hang unless the starter catches and completes the future. The coroutine itself has already failed, so that failure is also reported to the uncaught-exception handler; this is an infrastructure failure, not a loader outcome, and one report from the coroutine plus delivery to the waiters is acceptable.
- Job completion is later than cancellation. After `close()` a cooperative loader still has to unwind (its `finally` blocks, and any `withContext(NonCancellable)` cleanup such as a budget refund, which may suspend) before the job completes and a public `invokeOnCompletion` handler runs. A loader that ignores cancellation completes the job only when it returns. Completing the futures from `close()` itself releases waiters at once; the late `f.complete(...)` from the body is then a no-op.
- `CompletableFuture.complete(value)`: "If not already completed, sets the value ... Returns `true` if this invocation caused this CompletableFuture to transition to a completed state, else `false`" (Java 11 API). Any number of completers (body, close sweep, starter re-check, completion handler) are safe.
- Insert-then-check argument (inference): `AsyncCache.asMap()` iterators are "at least weakly consistent" and may miss an entry added after the iterator was created. If `close()` sets the closed flag *before* it iterates, and a starter reads the flag *after* its `cache.get` has inserted the future, then either the sweep sees the future or the starter sees the flag set. The flag must be an atomic or volatile.

### F7. `runTest` 1.10.2 and the shared scheduler (documented)

- Built-in timeout: "There's a built-in timeout of 60 seconds for the test body" (`runTest(timeout = DEFAULT_TIMEOUT.getOrThrow())`, system property `kotlinx.coroutines.test.default_timeout`). It uses `withTimeout` in the `runBlocking` that hosts the test, so it is real time, not virtual.
- While the body is suspended, a runner coroutine executes the scheduler's events one at a time (`tryRunNextTaskUnless`), advancing virtual time as needed. While the body is running (not suspended) nothing else runs, which is what makes interleavings deterministic.
- After the body: `scope.join()` waits only for the `TestScope`'s own children, then in `finally`: `backgroundScope.cancel()`, `testScheduler.advanceUntilIdleOr { false }` and `val uncaughtExceptions = scope.leave()`, then `throwAll(...)`. The condition `{ false }` never stops, so **every** remaining event on the shared scheduler runs, foreground or background, advancing virtual time as far as needed. A queued load coroutine on the cache's `StandardTestDispatcher`, a pending `delay` in a loader, a cancelled coroutine's dead task: all run during this drain, and they run before `leave()`, so an uncaught exception from them is still collected and fails the test. A coroutine on the cache's scope is not a child of the test, so it produces no "active child jobs" failure. An unbounded loop on the scheduler would make the drain never end (not applicable: no periodic work is scheduled).
- `StandardTestDispatcher.dispatch` is `scheduler.registerEvent(this, 0, block, context) { false }`: it queues, never runs inline. `TestCoroutineScheduler.runCurrent()` loops `events.removeFirstIf { it.time <= timeMark }`, so it also runs events that were enqueued by the tasks it just ran at the same virtual time. `advanceTimeBy(d)` leaves tasks due exactly at the target; `VirtualClock.advanceBy` adds the `runCurrent()`. `TestDispatcher` implements `Delay`, so a `delay` or `withTimeout` inside a loader running on `VirtualClock.dispatcher` is virtual.
- A coroutine suspended in a test-dispatcher `delay` that is cancelled loses its scheduled event (`continuation.disposeOnCancellation(handle)`), and its resume-with-cancellation is dispatched as a new event at the current time; it runs on the next `runCurrent()`/`advanceBy(Duration.ZERO)`, not inside `cancel()`.

## How comparable projects do it

- **Aedile 3.0.4** (`Cache.get`, tag `v3.0.4`): `CoroutineScope(coroutineContext.minusKey(Job) + SupervisorJob())` per call, `cache.get(key) { k, _ -> scope.future { compute(k) } }.thenApply { it }.await()`. The private `thenApply` future per caller is its fix (PR #67) for `CompletableFuture.await()` cancelling the shared future. It has no `close`, completes the shared future exceptionally on any failure, and the load runs in the first caller's context minus its Job. Useful as the confirmation of the `await` hazard; not a model for the end of a load.
- **kotlinx-coroutines' own `future { }`** (`CompletableFutureCoroutine`, 1.10.2): `onCancelled` completes the future exceptionally with whatever the cause was and `future.handle(coroutine)` cancels the coroutine when the future completes by any means. That coupling is right for a one-shot future and wrong here (a shared future must not be able to cancel the load), which is why the cache completes its future by hand from a `launch`.
- **Store5** (`FetcherController`, `5.1.0-beta01`): one ref-counted fetch per key in a library-owned scope, closed when the last downstream leaves; see the stack-level cache research, F4 and Consideration 1. The cache here chooses run-to-completion instead, so there is no multicaster to race.
- **Ktor `HttpTimeout`** (tag `3.4.0`): the timeout cancels the request's execution context with a domain cause (`executionContext.cancel(cause.message!!, cause)` where `cause = HttpRequestTimeoutException(request)`), and `unwrapRequestTimeoutException { }` catches the `CancellationException` and rethrows `cause.unwrapCancellationException()`, i.e. the domain exception, at the boundary. The same shape as converting a loader's cancellation into a typed failure at the cache boundary.
- **This module's `CallBridge.kt`** (`awaitHop`): `suspendCancellableCoroutine`, `invokeOnCancellation { call.cancel() }`, and a `settle` helper that resumes the continuation exactly once with a value from a `finally`, never a throwable, so an `Error` out of a handler still resumes the caller and still propagates. The load completion here follows the same discipline: one completion, a value, and a `finally`-like guarantee that something completes the future.

## Pitfalls and regrets

1. **Mapping every `CancellationException` to `Closed`.** A `withTimeout` inside a loader is a normal thing to write; with the cause-only handler it turns a timeout into a closed cache for every waiter while the cache stays open (F3).
2. **Letting an `Error` leave the `launch` body.** Reported by `launch` (thread handler or test collector), then reported again by Caffeine's `WARNING` log when the future is completed exceptionally, then maybe re-created under `-ea` (F1, F4, F5; Caffeine's logging is in the stack-level research, F2).
3. **Depending on job completion for liveness.** A loader that ignores cancellation, a slow `finally`, a rejecting dispatcher: all leave waiters hanging (F6).
4. **Using the internal `onCancelling` overload to get prompt notification.** It compiles only with an `@InternalCoroutinesApi` opt-in and is documented as not for use (F2).
5. **`UNDISPATCHED`/`ATOMIC` starts.** The first runs the loader's first segment in the caller's thread; the second runs the loader after `close()` (F2). A consumer who passes `Dispatchers.Unconfined` (or `UnconfinedTestDispatcher`) as `loadDispatcher` also gets the load's first segment inline inside `launch`, because `isDispatchNeeded` is false; the post-`get` start keeps that off Caffeine's per-key lock but not out of the caller's thread, so the KDoc of `loadDispatcher` should say it must dispatch.
6. **`async` under a supervisor.** Silent for an unawaited failure (F1).
7. **A test cache left open.** The drain at the end of `runTest` runs its leftover work (F7), and a leaked real-dispatcher load that throws after `leave()` fails the next test (F5). Close it (`use { }`), and use only `VirtualClock.dispatcher` for Level 2.
8. **`join()` as the assertion for "does not hang".** A hang then costs 60 s of real time and a vague failure; assert `isCompleted` after `advanceBy` instead.
9. **Treating the failed `launch` as a loader outcome.** A throwing `launch` leaves a joined future open (F6); catch around the starter.

## Recommendation for this repo

Keep the stack-level shape (cache-created future, start after `get`, scope with no parent, `asDeferred().await()`), and change the ending of a load as follows. Names are provisional; this is the shape, not final code.

```kotlin
// Outcomes of the shared future. Only Loaded has a lifetime; the others expire at once and are removed by identity.
private sealed interface Outcome {
    class Loaded(val lookup: Lookup<*>) : Outcome
    class Failed(val failure: Exception) : Outcome   // never a CancellationException
    class Fatal(val error: Throwable) : Outcome      // an Error (or any non-Exception): rethrown by every waiter
    object Closed : Outcome
}

// started by the one call whose mapping function ran, after cache.get returned
private fun startLoad(f: CompletableFuture<Entry>, ...) {
    if (closed.get()) { f.complete(Entry.closed()); return }                       // insert-then-check
    val job = try {
        scope.launch { f.complete(runLoad(...)) }                                  // DEFAULT start; the body never throws except to cancel
    } catch (t: Throwable) {                                                       // the dispatcher refused: launch failed its coroutine and rethrew
        f.complete(Entry.fatal(t)); return
    }
    job.invokeOnCompletion { cause ->                                              // safety net; first completer wins
        f.complete(if (cause == null || cause is CancellationException) Entry.closed() else Entry.fatal(cause))
    }
}

private suspend fun runLoad(...): Entry = try {
    toEntry(catchNonFatal { loader() })        // Result.failure(CancellationException) from the loader is routed like a thrown one
} catch (e: CancellationException) {
    currentCoroutineContext().ensureActive()   // close(): throws, the job ends cancelled, close() has already released the waiters
    Entry.failed(loaderCancelled(e))           // the loader's own cancellation: a typed failure, cause = e, never e itself
} catch (t: Throwable) {
    Entry.fatal(t)                             // delivered to the waiters as a value; not reported anywhere else
}

override fun close() {
    if (!closed.compareAndSet(false, true)) return
    scope.cancel()
    cache.asMap().values.forEach { it.complete(Entry.closed()) }   // first-wins; releases waiters without waiting for the loaders to unwind
}

// waiter
val entry = try { f.asDeferred().await() }
            catch (e: CancellationException) { currentCoroutineContext().ensureActive(); Entry.closed() }
// then: remove zero-lifetime entries by identity, and map Loaded -> success, Failed -> failure, Closed -> Closed("cache"), Fatal -> throw error
```

Reasoning in brief: the shared future carries a value in every case, so Caffeine never sees an exceptional completion, `asDeferred` never unwraps or re-creates anything, and the only exceptions that can reach a waiter are its own cancellation and a fatal `Error` it rethrows itself. The load coroutine ends normally or cancelled, never failed, so `launch` and the exception collector have nothing to report. Liveness comes from three independent completers (the body, `close()`'s sweep with the insert-then-check, and the completion handler), none of which depends on the loader cooperating. Use `launch`, `DEFAULT` start, no `CoroutineExceptionHandler`: with the body total, a handler would only hide an unexpected infrastructure failure, which `launch` reports loudly.

I would reject: `async` (no result channel needed; silent for unexpected failures); `CompletableDeferred` as the shared object (Caffeine needs the `CompletableFuture`, and the per-call `asDeferred()` is the documented bridge); `CoroutineStart.ATOMIC`/`UNDISPATCHED` (F2); `invokeOnCompletion(onCancelling = true)` (internal API); and the cause-only handler of the stack-level shape (F3, F6).

### Level 2 tests on `VirtualClock`

Build each test as `runTest { val clock = virtualClock(); val cache = CaffeineResponseCache(timeSource = clock.timeSource, loadDispatcher = clock.dispatcher, maintenanceExecutor = clock.maintenanceExecutor); cache.use { ... } }`. Test coroutines launched with `launch`/`async` in the body run on the test's `StandardTestDispatcher`, on the same scheduler; `clock.advanceBy(Duration.ZERO)` runs everything due now (waiters start, the load starts, the loader suspends in its `delay`). Assert with `isCompleted`, `isCancelled` and the recorded result, never with `join()`.

|---|---|---|
| One waiter cancels while the load runs | two `async { cache.getOrLoad(k) { delay(1.seconds); ... } }`; `advanceBy(ZERO)`; `w1.cancel()`; `advanceBy(ZERO)`; `advanceBy(1.seconds)` | `w1.isCancelled`; `w2` completed with the value; loader ran once; entry stored (a later call is a hit) |
| Every waiter cancels | as above, cancel both | after `advanceBy(1.seconds)` the loader finished and a later call is a hit |
| Load in flight at `close()` | two waiters; `advanceBy(ZERO)`; `cache.close()`; `advanceBy(ZERO)` | both `isCompleted` with `Closed("cache")` and neither cancelled; the loader observed its cancellation (flag set in `finally`); `close()` twice does not throw; a later call returns `Closed` |
| Loader ignores cancellation | loader `withContext(NonCancellable) { delay(10.seconds) }`; `close()`; `advanceBy(ZERO)` | the waiters are already `Closed` although the loader is still in its `delay`; then `advanceBy(10.seconds)` leaves them unchanged |
| Close between `get` and the start | `loadDispatcher` = a test-local parking dispatcher whose `dispatch` appends the `Runnable` to a list; waiter via `launch`; `advanceBy(ZERO)` (the waiter is suspended, the load is parked); `cache.close()`; run the parked tasks | waiter `Closed`; the loader's first line (a flag) never ran; no exception reaches `runTest`. The parking dispatcher is not a `Delay`, so the loader must not `delay` in this case |
| Loader's own cancellation | loader `{ withTimeout(1.seconds) { awaitCancellation() } }`, plus variants that `throw CancellationException("x")` and that return `Result.failure(CancellationException())`; `advanceBy(1.seconds)` | waiter result is a failure whose `exceptionOrNull()` is not a `CancellationException` and is not `Closed`; the waiter's job is neither cancelled nor failed; a second call for the same key runs the loader again; a call for another key still works (the cache is open) |
| Fatal `Error` | loader `{ throw Boom() }` with `class Boom : Error()`, two waiters | each `assertFailsWith<Boom>` and `assertSame` to one instance; `runTest` completes normally (nothing reached the collector); a third call reloads; the entry is gone |
| No hang, per case | after each `advanceBy`, `assertTrue(w.isCompleted)` | a hang fails an assertion at once instead of timing out |

The one interleaving not reachable deterministically through a public seam is `close()` landing after the entry's closed-check but before `cache.get` returns (the insert-then-check path). The parking dispatcher covers its consequence (a load whose scope is already cancelled). A Level 4c repetition test (many threads calling `getOrLoad` while another closes, every call must return within a bound) can exercise the window itself, but it is probabilistic.

### Considerations

1. **An `Error` with no waiter left.** If every waiter has cancelled when the loader throws an `Error`, nobody receives it, and nothing else reports it. Options: (a) accept it (a load nobody awaits has no consumer, the entry is removed, the `failedLoads` counter can count it); (b) log it at `ERROR` from the body, which reports it a second time whenever a waiter also rethrows it; (c) rethrow from the body when `f.complete(...)` returns false (the sweep already delivered `Closed`), which sends an undelivered `Error` to the uncaught-exception handler only in that case. Recommendation: (a), plus (c) if the closed-race should not lose an `Error`; (c) makes a Level 2 test that closes the cache while a loader throws an `Error` fail through the collector, so such a test would have to avoid that combination.
2. **Which failure a loader's own cancellation becomes.** The failure model has `TransportFailure.Timeout(cause)` for a timeout and no leaf for "the load was cancelled". Options: (a) `TransportFailure.Timeout(cause = e)` for a `TimeoutCancellationException`, and a new `HttpFailure` leaf for any other `CancellationException` (`HttpFailure` documents that "new leaves may be added in a feature release"); (b) one new leaf for both; (c) a cache-internal exception type, not matchable by consumers. Recommendation: (a). The rule that matters for correctness is fixed: never a `CancellationException`, original kept as `cause`.
3. **A cancelled caller on the hit path.** The hit path never suspends, so a cancelled coroutine receives a value. Options: leave it (conventional for a function that does not suspend) or call `currentCoroutineContext().ensureActive()` first (cheap, makes "a cancelled caller always gets `CancellationException`" true). Recommendation: add the check.

## Gaps

- **Nothing was run.** Every behaviour above is read from source, KDoc and the library's tests. The unit tests that would establish the points that matter most: (1) `close()` with a parking `loadDispatcher` (the close-before-start row of the table) to confirm the waiter is released before the parked task runs and the loader body never executes; (2) the loader-cancellation row, to confirm `isActive` is true after catching a `TimeoutCancellationException` out of the loader and that the waiter's job is untouched; (3) the non-cooperative-loader row, to confirm `close()` releases waiters while the loader is still suspended in `NonCancellable`; (4) a fatal-`Error` row asserting `assertSame` under `-ea`, to confirm identity survives (it should, since the error is rethrown from a field, not through `await`).
- **The residue of a cancelled waiter on the shared future** (the `handle` callback and one `CompletableDeferred`, released when the future completes) is inferred from the structure of `asDeferred` and from how `CompletableFuture` stores dependents; I did not read the JDK's `postComplete`, and I did not measure it. If the bound mattered, a test that cancels 100,000 waiters on one slow load and checks heap growth would settle it.
- **That Caffeine never cancels a future it holds** (on eviction, `invalidate` or `remove`) is assumed, not sourced. The waiter guard (`catch CancellationException` then `ensureActive()`) is written so the requirement holds even if it did; that branch cannot be reached from a Level 2 test without reaching into the cache.
- **The insert-then-check argument** relies on weakly consistent iteration reflecting entries present when the iterator was created. The Caffeine Javadoc states the "undefined" part for later changes; the guarantee for earlier ones is the usual `ConcurrentHashMap` behaviour, not quoted here. Only the Level 4c repetition test can probe it.
- **The exact cause object** that a job cancelled before start hands to a late `invokeOnCompletion` handler (the scope's `JobCancellationException`, from `getChildJobCancellationCause`) is read from source; the design only relies on it being a `CancellationException`.
- **Fan-out of the test exception collector across tests in one JVM** is stated by its KDoc; whether this repository ever runs test classes in parallel inside one JVM was not established (no parallel setting was found in the build files I searched, `build-logic` and the module's `build.gradle.kts`). If it does, a leaked exception could fail a neighbouring test.
- **The failure leaf for a loader's own cancellation** is not settled by the failure model as it stands (Consideration 2).
- **Non-JVM targets:** the cache is `jvmMain` only; none of this was checked for `js` or native, where `asDeferred`, `ServiceLoader` and `Thread.uncaughtExceptionHandler` do not exist.
- **Host and versions:** kotlinx-coroutines and `-test` 1.10.2, Caffeine 3.3.1, Java 11 API; read on 2026-11-02. I did not check whether 1.10.3 or a later release changed `asDeferred`, `ExceptionCollector` or `runTest`.
