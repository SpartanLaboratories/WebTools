webtools-http

The common core of a suspend HTTP stack for Kotlin: the request and response types, a canonical Url that parses like OkHttp's HttpUrl and is only ever stricter, a typed failure model returned inside Result, and the transport and wall-clock ports a consumer calls or, with the opt-in, implements. No transport, cache or budget is built yet: those are the stack's later units, drawn dashed.

Lifecycles and rules

    
A transport's life, how values are built, and the rules the module holds to.

    

      
A transport's life HttpTransport's contract

        
  1. constructed by its implementation (none ships yet)
  2. execute(request): one request per hop, never a retry; concurrent calls allowed
  3. a status in 100..599 is a response, a 304 included; outside it, Protocol
  4. close(): idempotent, non-suspending, never throws
  5. after it, execute returns HttpFailure.Closed("transport")

        
Cancellation is thrown, never wrapped in a Result.

      
Building a value the factories

        
  1. HttpHeaders { add(name, value) }: names are RFC 9110 tokens, values hold no CR, LF or NUL
  2. HttpRequest(method, url) { … } refuses, in order: CONNECT, an unsendable value, a body on GET, HEAD or TRACE, a second content type
  3. HttpResponse(status, url) { … } takes 100..599; RedirectHop 300..399

        
A developer-written value throws IllegalArgumentException at construction; text from outside the process returns Result.

      
Rules the module holds to

        
Values are immutable. Byte arrays are copied in and read back as copies, so a response shared by several callers cannot be changed by one. Url, HttpMethod, HttpHeaders, RedirectHop and the reasons compare by value; HttpRequest, HttpResponse and RequestBody by identity.

        
Nothing prints a secret. toString() shows names, the method or status, the redacted URL and sizes, never a header value or a body; a failure's message is constant text plus named non-sensitive fields.

        
Common code stays common. webtools-http-commoncheck compiles commonMain for js in check, so a JVM API there is a compile error.

Guarantees

  

    
Failure model

      
  • Url.parse and HttpMethod.of return Result.failure(IllegalArgumentException) with a constant message that never echoes the input.
  • A port returns its HttpFailure inside the Result: a TransportFailure leaf, an UpstreamFailure, or Closed after close().
  • Thrown, not returned: IllegalArgumentException from a factory given a broken developer-written value; cancellation.
  • Retried inside: nothing; a transport sends one request per hop.

    
Extension points

      
  • HttpTransport, WallClock — implement Experimental behind @OptIn(ExperimentalForInheritanceWebToolsApi::class); calling and passing them are Stable Core
  • HttpFailure, TransportFailure, UpstreamFailure — subclass Experimental, the same marker
  • RefusalReason, ExhaustedReason — may gain constants; keep an else Stable Core
  • Every other public type is final or a factory Stable Core

Compatibility & versioning

      
  • Version 1.0.0, from the root default: new, unreleased, not on Maven Central until the HTTP stack is complete.
  • Checked: the ABI dump api/webtools-http.api (294 lines) by apiCheck, and the Java 11 floor by verifyJavaFloor, both in check. The dump does not record @SubclassOptInRequired, and no permanent check proves the gate.
  • Experimental seams may change in a minor release; Stable Core changes only in a major.

    
Thread safety

      
  • Safe to share: every value type, which is immutable, and WallClock.System, which is stateless.
  • HttpTransport.execute may be called concurrently and is main-safe; a WallClock implementation must be safe for concurrent calls.
  • Confined: a builder, reachable only inside its factory's lambda.

    
Resources to close

      
  • HttpTransport is AutoCloseable: close() is idempotent and never throws; the default does nothing.
  • No other type holds a resource, and no transport implementation ships in 1.0.0.
