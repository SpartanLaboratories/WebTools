Gradle build

Lifecycles and rules

    
The order a build configures in, the path from source to a release, the TestKit home's life, and the rules the scripts hold to.

    

      
Configuration order every ./gradlew run

        
  1. wrapper starts Gradle 9.7.1
  2. settings: includeBuild("build-logic"), first
  3. foojay 0.8.0 · include 5 modules
  4. root: allprojects group, version 1.0.0
  5. a module requests its plugin: build-logic compiles, then is cached
  6. the plugin applies Kotlin at JAVA_FLOOR 11, publishing, test dependencies
  7. registerVerifyJavaFloor, into check
  8. registerLevelTasks: 7 tasks, lazily
  9. the module's own lines: dependencies, coordinates, POM

        
Versions live in one file. Kotlin 2.2.0, vanniktech 0.36.0 and binary-compatibility-validator 0.18.2 are plugin markers at literal versions in build-logic/build.gradle.kts; the scripts apply plugins by id, and Gradle forbids versions there.

      
Source to release the path every module takes

        
  1. compile to Java 11 bytecode on the build JDK
  2. test: every class
  3. check: verifyJavaFloor
  4. gatingTest … uatTest, on demand
  5. signAllPublications
  6. publishToMavenCentral

        
No CI and no release record. Who runs publishToMavenCentral, and when, is not recorded in the repository; there is no CI, CHANGELOG or release tag yet. A release needs the Central credentials and a signing key as Gradle properties, never committed.

      
The TestKit home and generated projects build-logic's nested-build tasks

        
What happens

          
Createdon the first nested-build run: build-logic/build/testkit/home, the TestKit directory and the nested builds' Gradle user home; it downloads the Kotlin compiler, the test dependencies and the plugin markers, so that run needs the network (about 910 MB measured)

          
Sharedby every nested build of integrationTest, e2eTest and nonfunctionalTest, one task at a time (testKitHomeLock), and kept between runs

          
Per test classa generated project under build-logic/build/testkit/projects/p-<label>-<base36>, built in @BeforeAll

          
Removedeach project, best effort in @AfterAll (a held file is logged as a WARN); clean resets both directories

        

      
Rules the scripts hold to

        
Level tasks select by package com.spartanlabs.testing.<level>.*; none is part of check. A module's level task passes when nothing matches; every one of build-logic's own fails on an empty run. A test class outside the level packages runs under test only.

        
One Java floor, read from one constant: WebToolsBuild.JAVA_FLOOR = 11 sets jvmTarget, -Xjdk-release and the Java compatibility in the JVM plugin, and the jvm() options and TargetJvmVersion in the multiplatform plugin; no module sets its own, and verifyJavaFloor fails one that does. No plugin sets a toolchain or explicitApi().

        
binary-compatibility-validator only on a multiplatform module, never at the root or on an ancestor; such a module commits api/<project>.api, because apiCheck fails until the dump exists (webtools-http/api/webtools-http.api, 294 lines). No module script may assign runtimeDependencyFiles.

        
The check-only js compile has no environment. webtools.kotlin-common-check calls js() with no nodejs() or browser(), so the target has no test task, nothing downloads Node.js or Yarn, no kotlin-js-store/ is written and the root project gains no task; the cost is one "JS Environment Not Selected" warning per configuration-cache miss. check depends on compileKotlinJs.

Guarantees

  

    
Failure model

      
    
        
  • A failing compile or test fails ./gradlew build; nothing is retried.
    • 
        
  • Configuration errors fail the build at configuration: a second level-task registration on one project throws InvalidUserDataException.
    • 
        
  • A module's level task passes on an empty selection; build-logic's own test tasks fail on one. A multiplatform module's apiCheck fails until its dump is committed. A JVM API in webtools-http's common code fails the check module's compileKotlinJs, in check.
    • 
        
  • verifyJavaFloor, in check, fails on a class above major 55 in a module's jars or runtime classpath, a library variant declaring another org.gradle.jvm.version, an unreadable input, or nothing to check; it lists up to 20 violations.
    • 
      

    
Extension points

      
    
        
  • For a module's build file: the plugin ids webtools.kotlin-jvm-library (three modules), webtools.kotlin-multiplatform-library (webtools-http), webtools.kotlin-common-check (webtools-http-commoncheck), webtools.published-library.
    • 
        
  • WebToolsBuild, a public object in the default package: LEVELS, LEVEL_PACKAGE_ROOT, registerLevelTasks, JAVA_FLOOR, classFileMajor, registerVerifyJavaFloor, readable from any module script.
    • 
        
  • A module that publishes another jar adds it to its verifyJavaFloor task's jars (the VerifyJavaFloor task type is public).
    • 
        
  • A module adds its own dependencies, coordinates, POM name and description, and anything that is its alone (webtools-udp's version and port lock; a multiplatform module's opt-in as a language setting of its main source sets). A check module adds the sibling's commonMain as a relative srcDir and its js actuals.
    • 
        
  • Unpublished, used only inside this repository: no stability tier or opt-in marker applies.
    •

101 tests in com.spartanlabs.testing.<level>.webtools.buildlogic, plus 8 harness classes in testing.support. ./gradlew :build-logic:test (L1 gating, L2 component, L4a deterministic: 47 tests) is the pre-commit gate; the three nested-build tasks (54 tests: integration 46, e2e 5, non-functional 3) run on demand; ./gradlew build runs none of them. No test-inspector report is committed, and no module test runs on a JDK 11: the level tests run on the build JDK, with no JDK 11 launcher yet.

    
Compatibility & versioning

      
    
        
  • The build has no version; it publishes nothing. Every module's class files are Java 11 bytecode (major 55) compiled against the Java 11 API, and its API and runtime variants declare org.gradle.jvm.version 11, whichever JDK 17 to 26 runs the build.
    • 
        
  • The floor rides in versions set in the modules' own build files: webtools-scraping and webtools-browser 1.0.0a, webtools-udp 2.0.0a, none published; Maven Central's 1.0.0 and 2.0.0 are Java 23 bytecode. A lettered version orders below the plain one, so a consumer requests it strictly.
    • 
        
  • Gradle 9.7.1 · Kotlin Gradle plugin 2.2.0 · vanniktech 0.36.0 · binary-compatibility-validator 0.18.2 on its own ASM (the pin went with the floor) · foojay 0.8.0.
    • 
        
  • Kotlin 2.2.0 prints a Gradle-10 deprecation at jvm() and at js() (KT-78620), and "JS Environment Not Selected" at the check module, so no build runs with --warning-mode=fail. Configuration-cache compatible: a second identical run reuses the entry. -Xjdk-release is an experimental Kotlin flag; verifyJavaFloor is its backstop.
    • 
      

    
Thread safety

      
    
        
  • No runtime threads: build-logic is never on a module's runtime classpath.
    • 
        
  • commonUdpPortLock (one permit) runs webtools-udp's test, integrationTest, e2eTest and nonfunctionalTest one at a time, so two never bind UDP 9998 at once.
    • 
        
  • testKitHomeLock (one permit) runs build-logic's three nested-build tasks one at a time on the shared TestKit home.
    • 
      

    
Resources to close

      
    
        
  • Nothing a module or a consumer holds.
    • 
        
  • The TestKit home (about 910 MB) stays between runs; clean resets it and any generated project a held file left behind.
    • 
        
  • A TestKit daemon outlives each nested build and is reused until its test JVM exits.
    • 
      

    
On your classpath

      
    
        
  • Nothing from the build itself: build-logic is never published and never on a module's runtime.
    • 
        
  • Through the Kotlin plugin it applies, each module's POM carries kotlin-stdlib:2.2.0; each module declares its own api(slf4j-api:2.0.13).
    • 
        
  • What a module ships is Java 11 bytecode whose metadata declares org.gradle.jvm.version 11, and verifyJavaFloor fails it when a runtime dependency holds a class above Java 11, so nothing it brings needs a newer JVM.
    • 
        
  • Test-only, from the plugins: kotlin-test, kotlin-test-junit5, logback-classic:1.5.6.
    • 
      

    
Releasing

      
    
        
  • publishToMavenCentral with signAllPublications(): every publication is signed.
    • 
        
  • Needs, as Gradle properties and never committed: mavenCentralUsername, mavenCentralPassword, and a signing key (signing.keyId, signing.password, signing.secretKeyRingFile, or the signingInMemoryKey trio).
    • 
        
  • A Kotlin/JVM module ships a sources jar and a javadoc jar; a multiplatform one (webtools-http, new at 1.0.0 and not released) sources jars and an empty javadoc jar. A check module publishes nothing.
    • 
        
  • check runs verifyJavaFloor before a release. The lettered versions that carry the floor are not published yet; the README's install block names Central's versions until they are.
    •
